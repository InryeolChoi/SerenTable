# 실제 worker 강제 종료·복구 검증

위치: **자동 매칭·실패 해결 → 예약 매칭·재배치·실패 해결 → 필수조건·중복·중단 복구 검증** (Work #6).

## 수행

- `tests/test_worker_crash_recovery.py`에서 실제 별도 worker 프로세스를 실행한다.
- 테스트 전용 PostgreSQL 트리거·advisory lock으로 테이블 배치 저장 후 마지막 성공 상태 저장을 대기시킨다. `pg_stat_activity`는 장애 주입 시점 동기화에만 사용한다.
- HTTP로 미커밋 실행 이력이 보이지 않고 1회권이 HELD인 것을 확인한 뒤 프로세스를 강제 종료한다. Python 예외 처리나 정상 종료에 의존하지 않는다.
- 장애 주입을 제거하고 새 worker를 실행한다. 결과는 운영자·참가자 API로 판정하며 업무 테이블을 직접 읽어 정답으로 삼지 않는다.

## 검증

- 로컬 PostgreSQL17의 별도 DB `serentable_worker_crash_test`, Python3.12에서 집중 시험 1개 통과(6.29초).
- 종료된 트랜잭션의 실행 이력·배치·권리 사용이 롤백되고, 새 worker가 4명·1테이블을 정상 확정한다.
- 확정 이전 1회권은 HELD·사용 시각 없음, 확정 이후 USED·사용 시각 있음이다. 한 번 더 실행해도 실행 이력과 이용권 사용 시각이 변하지 않는다.
- 실제 중단은 미커밋 실행 세대도 롤백하므로 재시작 성공의 attempt는 1이다. 기존의 저장된 RUNNING → ABANDONED 시험은 별도의 지속된 중단 상태 fixture이며 실제 프로세스 종료와 동일시하지 않는다.
- 관련 매칭 회귀 합계 **18개 PASS**(69.53초), Ruff check·format PASS. 독립 Spec 검토에서 마지막 재실행이 오류 없이 완료됐는지 추가 확인하도록 보완했다.
- 운영 DB·원본 준비 DB는 사용하지 않았다. 제품 코드·스키마·정책 변경은 없다. 전체 CI는 [PR #35 checks](https://github.com/InryeolChoi/SerenTable/pull/35/checks)에서 확인한다.

## 남은 항목

일정 이동·권리 보관/재사용·멤버십 연장·환불·제외 관계 입력이 구현되면 관련 장애 검증을 추가해야 한다. 따라서 이 Task와 Work #6은 **진행 중**이다. 운영 환경 장애 주입이나 실제 기기 검증을 수행한 결과가 아니다.

- 기존의 저장된 RUNNING 상태 복구와 실제 프로세스 종료에 따른 트랜잭션 롤백을 구분했다.
