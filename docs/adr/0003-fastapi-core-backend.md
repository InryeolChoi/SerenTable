# TypeScript 화면과 FastAPI 핵심 업무 서버로 책임을 나눈다

참가자 모바일 웹과 운영자 화면은 TypeScript로 개발하고, 신청·이용권/모의결제·매칭·확정·환불·예외 등 핵심 업무 상태 변경은 한 FastAPI 서버에 모은다. Python 서버 안에서 업무 모듈의 경계를 나누되 별도 마이크로서비스를 늘리지 않는다. 인증·DB 운영·실시간 전송에는 관리형 서비스를 활용하는 방향으로 검토하며 공급자와 작업 실행 구조는 후속 결정이다.

TypeScript 단일 구성은 연결·배포 부담이 작지만, 사용자에게 있는 Java/Spring·Django·인증 경험을 활용해 업무 서버의 트랜잭션·멱등성·복구를 직접 설계하고 검증하는 경험을 우선했다. Python 매칭 전용 구성 대신 핵심 업무 책임을 Python으로 모아 같은 상태를 두 서버에서 수정하는 복잡성을 피한다. 추가된 프론트/서버 API 계약과 배포 검증 비용은 감수한다.

수상 여부와 무관하게 운영 자동화 신뢰성을 주력 성과로 남기고, 매칭은 필수조건 검사와 작은 데이터 정답 비교를 확보한다. 구체 프론트 프레임워크, DB 공급자, ORM, 최적화 알고리즘과 호스팅은 아직 확정하지 않았다.

결정 근거: [인터뷰 Q4 최종 선택](../design/mvp-interview.md)의 추천 C에 대한 사용자 답변 “그렇게 하자”, Q7의 기존 경험 및 Q8의 검증 목표. ADR-0001의 이전 TypeScript 단일 방향을 대체한다.

후속 결정: 프론트는 ADR-0005의 React·Vite CSR, 배포·DB는 ADR-0004의 Railway·PostgreSQL, 작업 실행은 ADR-0006의 별도 실행기를 적용한다. 관리형 인증·Realtime 제공자 검토는 Railway 단일 플랫폼 결정으로 대체되었으며 구체 인증·채팅 라이브러리는 미정이다.
