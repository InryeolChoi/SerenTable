# 구현 전 설계와 기존 작업 구조의 연결

기준: 2026-10-16, Asia/Seoul. 사용자가 A안과 아래 배치를 승인하고 Blaybus 등록을 완료했다고 확인했다. 후속 병렬 실행 요청에 따라 설계 3종을 작성·검토했고 [Task별 결과](./parallel-task-results.md)에 연결한다. 업무 기능 구현·데이터 적재는 아직 시작하지 않았으며 전체 물리 스키마·미결정 정책을 동결하지 않는다.

## 확정한 범위

사용자가 A안을 선택했다. 핵심 ERD·데모 데이터 변환 규칙·기능별 보안 검증 기준을 먼저 확정한다. 핵심 관계·식별자·상태·무결성 제약을 정하고 세부 필드는 각 기능 Work에서 보완한다. 전체 물리 스키마를 한 번에 동결하지 않는다.

제공 데이터는 원본 보존과 변환 규칙 승인을 거쳐 실행 가능한 데모 시드로 적재한다. 294개 응답을 그대로 294명의 계정으로 취급하거나 누락값·결제·이력을 사실처럼 생성하지 않는다. 이번 논의로 U01/U02/U16/U17 등의 세부 정책이 해결된 것은 아니다.

## 승인·등록한 배치

기존 다섯 Agenda를 유지한다. 데이터·UI·보안은 각 기능의 완성 조건이므로 별도 Agenda로 분리하지 않는다. 완료된 자료 검토와 배포 Task 상태도 유지한다.

```text
개발·배포 기반 확보
├─ 요구사항·설계·자료 정리 — 기존 자료 검토 결과 유지
├─ 첫 배포·CI·DB 연결 — 남은 운영·원격 검증 계속
└─ 핵심 데이터·화면·보안 설계 [신규 등록]
   ├─ 핵심 ERD·상태·무결성 제약 설계
   ├─ 공통 UI·핵심 화면 흐름 설계
   └─ 개인정보·권한·보안 검증 기준 정리

참가 신청·이용권·결제
├─ 로그인·프로필·동의
│  └─ 기존 구현 Task에서 화면·입력/API 계약·권한을 함께 설계·구현
└─ 일정 신청·이용권·모의 결제
   └─ 기존 흐름 구현 Task에서 신청·결제 상태별 화면과 실패 동작 설계

자동 매칭·실패 해결
├─ 규칙·데이터·정답 기준
│  ├─ 입력 정규화·누락값·식별 정책 결정 — 기존 Task
│  ├─ 가상데이터 변환·DB 시드 구축 [신규 등록]
│  └─ 기존 100명 실행 사례·작은 정답·점수 기준 준비
└─ 예약 매칭·재배치·실패 해결
   └─ 기존 구현 Task에 대기·확정·실패·이동/보관/환불 화면 포함

모임 안내·피드백·재방문
└─ 기존 안내·채팅·피드백 Work에서 각 화면 설계·구현·권한 검증

운영자 예외·최종 검증·제출
└─ 기능별로 만든 어드민을 종합하고 E2E·보안 회귀 검증
```

## 추가·변경 이유와 완료 기준

| 변경 | 이유 | 완료 기준·범위 |
|---|---|---|
| 공통 설계 Work 1개·Task 3개 추가 | 화면의 행동, 업무 상태, 저장 관계와 공개 권한을 기능 구현 전에 맞추어 재작업을 줄임 | 핵심 ERD·상태/무결성 제약표, 참가자/운영자 화면 흐름과 간단한 스케치, 역할별 공개/수정 권한표·거절 테스트 기준. 기능별 물리 스키마·모든 화면의 최종 디자인은 후속 Work에서 완성 |
| 데이터 Work에 DB 시드 Task 1개 추가 | 완료된 자료 감사와 정책 결정만으로 실제 DB 적재가 구현되지는 않음 | 승인된 변환 규칙과 준비된 업무 스키마를 사용한 재실행 가능한 적재, 중복 방지, 원본/생성 데이터 구별, 적재 결과 검증. 데이터 계정의 로그인 범위·시드 실행 권한도 정함 |
| 기능별 기존 Task의 완료 기준 보강 | UI나 권한을 마지막 Work에 몰지 않기 위함 | 각 Work 착수 시 화면별 행동·상태·입력·오류·비공개 필드를 설계하고, 구현 후 API와 UI에서 검증. 화면이 없는 데이터 준비 Task에는 UI를 강제하지 않음 |

공통 UI 설계는 브랜드 참고 방향·기본 글자/버튼/폼/상태 표현과 사용자 이동 경로를 먼저 정한다. 로딩·빈 상태·실패·접근 거절도 포함한다. 기능별 설계는 그 기능 구현 바로 앞에서 구체화한다. 운영자 화면도 각 기능 Work에서 필요한 최소 흐름을 만들며 마지막 종합 Work까지 미루지 않는다.

핵심 설계 Work는 초안과 검토를 합쳐 1~2시간을 목표로 제한한다. 실제 소요 시간은 정책 결정량에 따라 달라지며 사용자가 기록한다. 데이터 시드 구현은 정규화 정책과 해당 업무 테이블이 준비된 뒤 수행하고, 나머지 데이터 Work의 기존 순서를 유지한다. 공통 설계가 길어지면 미결정 내용을 해당 기능 Work의 선행 조건으로 남긴다.

사용자가 Work 1개·Task 4개 등록 완료를 확인했다. Blaybus Work 하나를 GitHub Issue 하나에 연결하여 [핵심 데이터·화면·보안 설계](https://github.com/InryeolChoi/SerenTable/issues/15)를 생성했다. 첫 배포 Work를 선행으로 두고 로그인 Work의 선행 조건에 공통 설계를 추가했다. 기존 [규칙·데이터·정답 기준](https://github.com/InryeolChoi/SerenTable/issues/5)에 시드 Task를 포함하고, 실제 적재에 필요한 신청·결제 Work를 선행으로 추가했다. 별도 Agenda나 기능별 UI Work는 추가하지 않는다. 기존 완료 Task는 유지한다.
