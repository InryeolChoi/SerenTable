# 우연한 식탁 MVP 구현 명세서

**산출물 위치:** 개발·배포 기반 확보 → 요구사항·설계·자료 정리 → 기술 결정 및 미결정 항목 정리

**기준:** 2026-10-15, Asia/Seoul. 공식 PRD v0.2, 사용자 제공 킥오프 기록·신청 폼, 설계 인터뷰, 승인된 ADR을 종합한다. PRD가 제품 요구사항의 기준이며 이 문서는 확정한 구현 방향과 미결정 사항을 구분한다.

**공식 보완(2026-10-16):** 사용자 전달 [Blaybus 안내·FAQ](official-faq-2026-10-16.md)를 함께 적용한다. 가격·멤버십 정책 등 명시된 값은 아래에 반영하고 개발자 재량은 미결정으로 유지한다.

**상태:** 테스트 경계 사용자 확인 완료. 제품 구현은 시작하지 않았다. Work 10개의 Issue 분할·의존성은 기준안으로 승인되었다. 진행 중 변경은 사용자에게 먼저 안내한다. 미결정 항목이 있는 기능은 해당 정책을 확정하기 전 완료로 처리하지 않는다.

## Problem Statement (문제 정의)

참가자는 신청 이후 결제·매칭·확정 상황과 다음 행동을 알기 어렵다. 매칭에 실패하면 다른 일정으로 옮기거나 환불받기 위해 운영자에게 별도 문의해야 한다. 참가 후의 선호·안전 피드백도 다음 만남에 일관되게 반영되지 않는다.

운영자는 신청서, 입금 확인, 수기 조합, 식당, 단체방, 개별 안내와 피드백을 서로 다른 도구로 관리한다. 참가자를 개별 확정하고 연락하는 반복 업무와 취소·노쇼·조건 충돌 때문에 운영 시간이 증가한다.

개인 개발자는 제한된 기간 안에 PRD P0와 12단계 E2E를 배포 환경에서 증명해야 한다. 결과물에는 중복 실행·상태 일관성·재시도·복구 문제를 어떻게 방지하고 검증했는지 설명할 수 있는 근거가 필요하다.

## Solution (해결 방안)

참가자 모바일 웹과 운영자 어드민을 제공한다. 신청·모의 결제·예약 매칭·재배치·자동 확정·가상 식당 배정·단체방·알림·참석·피드백·다음 추천을 연결한다. 정상 흐름은 운영자 승인 없이 처리하고 자동으로 해결하지 못한 예외만 운영자에게 전달한다.

React·TypeScript·Vite의 CSR 화면을 FastAPI가 제공한다. 핵심 업무 처리는 한 Python 코드베이스에 모듈을 나누어 구성한다. API, 별도 작업 실행기, PostgreSQL을 Railway 한 프로젝트에 배포한다. 인증·채팅은 검증된 라이브러리를 활용하되 권한·저장·재연결·실패 처리는 검증한다.

심사용 배포 MVP를 목표로 하며 개발 완료 목표는 10/20, 제출 마감은 10/21 23:59이다. 월 운영비 상한은 3~5만원이다. 실제 비용과 완성 가능성은 배포 후 사용량 및 실제 가용 시간으로 검증하며 계획표만으로 달성됐다고 간주하지 않는다.

## Implementation Decisions (구현 결정)

### 1. 결정 상태와 기준

| 구분 | 의미 | 적용 |
|---|---|---|
| 확정 | 사용자 승인 또는 적용할 PRD 요구 | 구현의 기준으로 사용 |
| 미결정 | 정책·수치·라이브러리 등이 정해지지 않음 | 관련 Task 구현 전 확정 |
| 검증 제안 | 합의한 목표를 실행할 테스트 경계 제안 | 사용자 확인 후 채택 |

최신 승인 ADR-0002~0007과 후속 인터뷰 결정을 적용한다. ADR-0001의 TypeScript 단일 방향은 대체되었다. 초기의 Vercel·Supabase 추천안, Issue 없는 운영안도 현재 구성이 아니다. 원본 자료의 운영 수치·기간을 서로 혼합하지 않는다.

### 2. 확정 기술·배포 구조

| 영역 | 확정 사항 |
|---|---|
| 화면 | React + TypeScript + Vite, CSR. 참가자·운영자 화면 |
| 서버 | FastAPI. 신청·결제·매칭·확정·환불 등 핵심 상태 변경 담당 |
| 실행기 | 같은 Python 코드베이스의 별도 상시 작업 실행기 |
| 저장소 | PostgreSQL. API·실행기가 일관된 업무 상태를 사용 |
| 배포 | Railway 단일 프로젝트. 앱·DB·실행기는 별도 서비스로 구성 |
| 화면 제공 | 빌드한 화면 파일을 FastAPI가 제공. 별도 Node SSR 서버 없음 |
| 인증·채팅 | 앱 내부에 검증된 라이브러리를 활용. 구체 구현 방식은 미정 |
| 자동화 | GitHub 기반 개발·CI/CD. CI 성공과 배포를 연결하는 구체 수단은 미정 |
| 비용 | 월 3~5만원 상한 목표. 사용량·DB·실행기·저장/전송 비용을 측정 |

한 플랫폼은 한 프로세스를 뜻하지 않는다. API와 실행기의 장애·재시작을 분리하면서 같은 제품·모듈을 사용한다. Redis·Celery·외부 메시지 브로커 도입은 확정하지 않았다. Railway 가입·서비스 생성·유료 과금·배포는 아직 실행하지 않았다.

### 3. 업무 모듈과 경계

| 모듈 | 책임 | 연결 결과 |
|---|---|---|
| 사용자·프로필·동의 | 인증된 사용자, 프로필, 선호, 동의·계정 상태 | 유효한 신청 가능 여부와 매칭 입력 |
| 회차·신청 | 모집 설정, 복수 후보, 제출·취소 | 유효 신청 후보 |
| 이용권·모의 결제·환불 | 이용권 선택, 결제 상태, 보관/이동/환불 | 유효한 참가 권리와 처리 이력 |
| 매칭 | 후보 구성, 필수조건 검사, 선호 평가, 분리·병합·재배치·확정 | 테이블 또는 미매칭 해결 |
| 식당 | 가상 재고, 배정, 대체 탐색, 재고 부족 예외 | 참가 안내에 필요한 식당 정보 |
| 채팅·콘텐츠·알림 | 방·멤버십·시스템 공지·대화·예약 발송·재시도 | 영속 메시지와 전달 이력 |
| 참석·피드백·재방문 | 체크인·노쇼 후보·평가·사람별 선호·이력 | 다음 매칭/일정 추천 입력 |
| 안전·예외·감사 | 차단·신고·조치·예외와 변경 이력 | 허용된 운영자 처리와 추적 |
| 작업 실행 | 예약·실행·재시도·중단 복구 상태 관리 | 운영자 수동 시작 없는 자동화 |

핵심 업무를 브라우저에서 직접 확정하지 않는다. API와 작업 실행기는 같은 업무 규칙을 사용한다. 모듈 내부를 별도 네트워크 서비스로 나누는 것은 이번 확정 범위가 아니다.

### 4. 프로필·신청 입력

- PRD 기준 이름·연락처·출생연도·성별·직업, MBTI·관심사·본인 성향·희망 상대 성향, 가격대·음식 제한·알레르기, 개인정보·운영 동의를 지원한다.
- 사용자가 요청한 Instagram ID를 수집 항목에 추가한다. 필수성·검증 규칙·공개 범위는 아직 미정이며 매칭 점수 입력으로 확정하지 않았다.
- 관심사는 사용자 목록의 11개를 기준으로 한다. 영화 및 드라마, 음악, 독서, 글쓰기, 운동, 맛집 및 카페탐방, 여행, 사진 및 영상, 전시 및 공연아트, 패션 및 뷰티, 자기개발 및 공부이다.
- 기존 폼의 ‘독서·글쓰기’ 통합값을 새 11개 분류에 어떻게 대응할지는 미정이다. 본인 성향과 희망 상대 성향은 별도 선택지이다.
- 기존 폼의 날짜 단일 선택 대신 PRD의 복수 날짜·지역 선택을 적용한다. 연도 없는 폼 날짜를 앱의 실제 회차로 그대로 사용하지 않는다.
- 출생연도와 현행 폼의 나이를 구별한다. 기준 연도·연령 차이 계산 및 표시 정책은 구현 전 정한다.
- 입력 UI와 서버 모두 필수값 누락을 확인해야 한다. 구체 필수/선택 구분과 필드 타입은 정해진 PRD 요구 외에는 확정하지 않았다.

### 5. 이용권·모의 결제·미매칭 해결

- 이용권은 PRD 우선의 1회권과 모의 구독(멤버십)이다. 공식 FAQ Q4에 따라 1회권 9,900원, 멤버십 1개월 35,000원·3개월 75,000원·6개월 120,000원을 적용한다. 현행 폼의 3회권을 구독과 동일시하거나 추가 필수 상품으로 넣지 않는다.
- 공식 FAQ Q5에 따라 멤버십은 기간 내 참여 횟수 제한이 없고, 매칭 실패 횟수만큼 이용 기한을 연장한다. 실패 1회당 연장 단위·기산점·멱등 처리 기준은 구현 전 확정한다.
- 결제·환불은 모의 상태 전환을 허용한다. 실제 결제/정기 청구 또는 금융기관 환불이 수행됐다고 표시하지 않는다.
- 매칭 실패 이후 일정 이동·이용권 보관·환불은 참가자가 선택한다. 시스템이 임의로 환불하거나 미동의 회차로 이동하지 않는다.
- 일정 이동은 기존 결제를 유지하고 새 회차의 매칭 대기로 전환한다. 중복 승인·중복 권리 사용·서로 충돌하는 해결 선택을 방지해야 한다.
- 환불 제한과 당일 취소·노쇼 정책을 결제 전 및 신청 완료 시 안내한다. 공식 FAQ Q1의 현행 기준은 화요일 24:00 이후 환불 불가다. 회차별 적용·매칭 마감과의 일치 여부·시스템 사유 환불의 적용 관계는 미결정으로 둔다.
- 구독 상품 기간과 무제한 참여 원칙은 공식 FAQ로 확정됐다. 연장 세부 규칙·갱신·만료·환불 금액·보관한 이용권의 재사용 조건은 아직 정하지 않았다.

### 6. 매칭 요구와 확정한 구현 방향

1. 회차별 마감 시각에 유효한 신청과 결제 완료자를 대상으로 실행한다.
2. 날짜·지역이 일치하고 4~6명, 연령 차이 8살 이내, 차단·신고·비선호 제외 관계 없음 등 필수조건을 만족해야 한다.
3. PRD의 연령대 → 성비 → MBTI → 관심사 → 희망 상대 성향 순의 평가와 새로운 사람 우선을 반영한다. 연령 차이 상한은 선호 점수와 별개인 필수조건이다.
4. 성향은 명시적인 대응 규칙표를 사용한다. ‘나와 비슷한 사람’과 ‘다른 자극을 주는 사람’을 구별한다. LLM의 임의 궁합 판단은 채택하지 않는다.
5. 선호조건 평가와 최소 점수 기준을 명시해야 한다. 가중치·점수표·최소값·목적함수·탐색 알고리즘은 아직 미정이다.
6. 4명 미만 조합 또는 조건 미충족 조합을 해제하고 동의한 날짜·지역의 다른 미확정 테이블을 탐색한다. 7명 이상 후보군을 유효한 크기로 분리하고 가능한 미완성 조합을 병합한다.
7. 재배치 순서는 같은 날짜·같은 지역, 같은 날짜·다른 선택 지역, 다른 선택 날짜·같은 지역, 다른 선택 날짜·다른 선택 지역이다. 범위 밖 일정은 추천 후 참가자 선택으로 이동한다.
8. 재배치 완료 후 필수조건과 인원을 다시 검증하고 자동 확정한다. 확정 조건의 일부만 만족한 테이블은 확정하지 않는다.
9. 같은 사용자를 동시에 두 테이블에 배치하지 않는다. 반복 실행에서도 중복 테이블·단체방·환불을 만들지 않는다.
10. 미배치자는 대안 제시 상태로 이동시키고 이유와 해결 선택지를 제공한다. 필수조건을 완화해 억지로 배치하지 않는다.
11. 점수·적용 기준·알고리즘 버전·분리/병합/재배치/확정·실패 이유를 기록한다. 타인의 개인정보·상세 점수는 참가자 설명에 노출하지 않는다.
12. 실행당 최대 100명을 성능 검증 목표로 삼는다. 현재 성능이나 전역 최적해가 보장됐다는 뜻은 아니다. 목표를 넘는 입력의 처리 정책은 미정이다.

복수 회차의 마감·후보 경쟁, 참가자 수 최대화와 점수 최대화의 우선순위, 신고 접수/확정의 제외 시점, 취소 후 확정 테이블의 처리 범위는 후속 결정이 필요하다.

### 7. 상태와 데이터 계약

신청·결제·매칭·참석 상태는 하나의 값으로 합치지 않는다. 다음 값은 PRD 정의를 유지한다. 구체 전이 그래프·전이 주체·경합 처리·복합 상태 불변식은 후속 설계에서 명시한다.

| 상태 축 | PRD 값 |
|---|---|
| 신청 | DRAFT, SUBMITTED, CANCELED |
| 결제 | PENDING, PAID, FAILED, REFUND_AVAILABLE, REFUND_REQUESTED, REFUND_PROCESSING, REFUNDED, REFUND_FAILED |
| 매칭 | WAITING, MATCHING, REALLOCATING, CONFIRMED, ALTERNATIVE_OFFERED, TRANSFERRED, NO_MATCH, EXCEPTION |
| 참석 | SCHEDULED, ATTENDED, CANCELED_EARLY, CANCELED_LATE, NO_SHOW |

노쇼 후보와 확정 NO_SHOW는 다른 개념이다. 후보의 별도 저장/판정 방식은 미정이다. TRANSFERRED와 새 회차 WAITING을 보존하는 신청/이동 이력 모델도 아직 정하지 않았다.

PRD의 데이터 개념은 다음과 같이 유지한다. 이는 확정된 물리 스키마나 테이블 이름을 지정하는 목록이 아니다.

| 개념 | 보관할 정보와 연결 |
|---|---|
| User·Profile | 계정 상태, 기본 정보, 출생연도·매칭 선호·식사 조건 |
| EventSlot·Application | 회차·복수 후보·희망 지역·이용권·분리된 상태 |
| MatchRun·DiningTable | 실행·알고리즘 버전·참가자·평가·처리/실패 이력 |
| Venue | 가상 식당·지역/시간별 재고·인원·배정 결과 |
| ChatRoom·Notification | 테이블 멤버십, 영속 대화/시스템 메시지, 예약·발송·재시도 결과 |
| MatchResolution | 대체 일정·참가자 선택·이동/보관/환불 결과 |
| Attendance·Feedback | 체크인·취소·노쇼, 만족도·재참여 의향·비공개 선호 |
| SafetyReport·ExceptionCase | 신고·조치·미해결 예외·처리 이력 |
| 작업·감사 기록 | 예약/실행/복구 상태, 변경 주체·시각·이전/이후 상태 |

API는 프로필·신청·모의 결제·상태 조회·대안 선택·채팅·체크인·피드백·안전·운영자 기능을 외부 행동으로 제공한다. 구체 URL, 요청/응답 스키마, 인증 토큰/세션, 오류 형식·멱등 키·실시간 전송 프로토콜은 결정되지 않았다. 미정 계약을 확정된 예시 API로 제시하지 않는다.

### 8. 식당·단체방·푸시·콘텐츠

- 가상 식당 재고를 지역·시간·인원 기준으로 자동 배정하고 저장한다. 외부 예약 API는 제외한다. 대체 식당도 없으면 운영자 예외로 남긴다.
- 테이블 확정과 단체방 생성·초대·식당 안내·예약 발송을 연결한다. 모든 부수효과가 한 외부 원자 작업이라고 가정하지 않으며 부분 실패 후의 정합성과 복구를 설계해야 한다.
- 채팅 메시지를 영속 저장하고 테이블 참가자만 허용된 대화에 접근하게 한다. 구체 WebSocket/SSE/기타 전송 방식과 재연결 계약은 미정이다.
- 실제 푸시와 앱 내 알림은 별개이다. 단체방 메시지나 앱 내 알림만으로 푸시 요구를 완료 처리하지 않는다. 허용·미허용·미지원 환경의 동작과 실제 지원 기기 수신을 검증한다.
- 확정 즉시 안내, 하루 전 리마인드, 행사 시작 시 대화 콘텐츠 자동 게시를 지원한다. 관심사·성향을 활용한 대화 주제는 최소 3개이다.
- 발송 실패는 재시도하고 반복 실패를 예외로 올린다. 횟수·간격·최종 실패 기준과 외부 전달 중복의 처리 정책은 아직 미정이다.

### 9. 참석·피드백·안전·운영자

- 체크인으로 참석을 기록하고 종료까지 미체크인한 사용자를 노쇼 후보로 운영자에게 보여준다.
- 테이블·대화·식당 평가, 재참여·추천 의향, 사람별 비공개 선호와 신고·차단을 수집한다. 미응답 1회 리마인드와 재신청 허용은 PRD 기준이다.
- 이전 만남과 비선호는 다음 매칭에 반영한다. 다시 만나고 싶은 선호와 새로운 사람 우선의 충돌, 만족도/노쇼 반영 가중치는 아직 정하지 않았다.
- 신고 내용·제외 관계·상세 개인정보를 다른 참가자에게 공개하지 않는다. 운영자도 허용된 권한으로만 접근하며 주요 변경 이력을 남긴다.
- 운영자는 회차·식당 재고·자동화 설정, 신청/결제/환불, 매칭/안내 이력, 예외·참석·피드백·안전과 CSV를 다룬다. 어드민은 정상 흐름의 수동 승인 관문이 아니다.
- 개인정보 삭제·탈퇴 후 보관, 로그 마스킹과 공개 필드, 신고 처리 기준을 정해야 한다. 확정 전 개인정보 비공개는 유지한다.

### 10. 제공 데이터와 브랜드 자료

- 제공 엑셀에는 이름이 있는 응답 294행이 있다. 서로 다른 이름 문자열은 258개이며 고유 사용자 수로 단정하지 않는다.
- 연락처·Instagram·직업은 비어 있고 MBTI의 대소문자·복수 응답·비표준값, 연도 없는 날짜, 항목 내부 쉼표가 있다. 단순 쉼표 분리·이름 병합·나이 역산·임의 오타 보정은 하지 않는다.
- 결제 완료, 이전 참석/만남·피드백·차단은 독립된 데이터로 제공되지 않았다. 신청·이용권 선택을 결제나 참석 완료로 간주하지 않는다.
- 원본을 보존하고 정규화 규칙과 생성/보완한 데모 데이터를 구분한다. 실행당 100명 목표를 맞추려고 원본을 잘라 덮어쓰지 않는다.
- 우연한 식탁 홍보 이미지와 와썹하우스 운영사 이미지·로고를 구분한다. 공식 FAQ Q12에 따라 로고 원본은 제공되지 않으며 유사 재현물을 사용할 수 있다. 원본 사진/PDF/얼굴의 공개 재배포까지 승인된 것으로 확대하지 않고 재현물을 공식 원본으로 표시하지 않는다.

### 11. 자동화의 신뢰성

확정한 목표는 중복 실행 방지, 트랜잭션 일관성, 재시도와 재시작 복구를 재현 가능한 근거로 증명하는 것이다. 예약과 처리 결과는 PostgreSQL에 보존한다. 메모리 타이머만으로 작업의 존재를 보관하지 않는다.

같은 회차/작업의 중복 실행, 동일 참가자 경쟁 배치, 일정 이동과 환불의 경쟁, 식당 재고의 경쟁 소비, 알림 중단/재개를 검증해야 한다. 잠금·임대·멱등 키·트랜잭션 경계·실패 주입 수단은 아직 미정이며 특정 구현을 이미 합의한 것으로 작성하지 않는다. 외부 알림의 무조건적인 exactly-once를 보장하지 않는다.

### 12. Agenda → Work → Task 실행과 추적

기본 진행 순서는 등록한 Agenda, 그 안의 Work, 해당 Work의 Task 순이다. 현재 작업은 첫 Agenda의 요구사항·설계·자료 정리 Work 안의 기술 결정 및 미결정 항목 정리 Task이다. 기존에 수행한 자료 확인은 실제 수행 결과를 기록하되 이후 구현이 완료된 것처럼 표시하지 않는다.

Work 하나에 GitHub Issue 하나를 연결하고 하위 Task는 체크리스트로 추적한다. PR은 검토 가능한 변경 단위로 만들어 관련 Task를 명시하며 Task와 강제 1:1 관계를 두지 않는다. Work의 일부만 완료한 PR이 전체 Issue를 자동 종료하지 않게 한다.

Task 종료마다 사용자가 수동으로 갱신할 Blaybus 경로, 상태, 수행·검증 문구와 실제 PR 링크를 제공한다. 전체 Work 완료 기준이 충족될 때만 Work 완료를 요청한다. 범위·일정·선행 관계가 달라지면 Agenda 수정 문구도 제공한다. 사용자 반영 확인 전에는 Blaybus 수정 완료라고 기록하지 않는다.

Work·Task 추가가 필요하면 이유·소속·완료 기준·일정 영향을 먼저 제시한다. 추가 항목을 조용히 등록하지 않는다. 실제 사용자 투입 시간과 예상 시간은 구분한다.

## Testing Decisions (테스트 결정)

### 1. 합의된 검증 목표

- 외부에서 관찰되는 행동과 상태·권한·처리 결과를 검증한다. 내부 함수 호출 횟수, 특정 ORM/클래스 구조에 맞춘 테스트를 기준으로 삼지 않는다.
- 운영 자동화 신뢰성을 주력으로 하고 매칭의 필수조건 검사·작은 데이터 독립 정답 비교를 확보한다.
- 구현과 검증의 판단을 분리한다. 검증 담당은 PRD·명세·공개된 입력/출력 계약으로 독립 시나리오를 만들고 구현 코드를 그대로 재작성한 기대값에 의존하지 않는다.
- 실행당 100명에서 필수조건 위반·중복 배치·참가자 누락·성공률·실행 시간·자원 사용량을 측정한다. 수용할 시간·메모리·최적해 차이의 수치는 아직 미정이다.
- 현재 저장소에는 실행 코드·기존 테스트·기존 테스트 경계가 없다. 기존 테스트를 재사용했다거나 검사에 통과했다고 주장하지 않는다.

### 2. 사용자 확인을 받은 테스트 경계

| 경계 | 검증 방식 | 피하는 검증 |
|---|---|---|
| 주 경계: 제품의 외부 행동 | 실제 PostgreSQL과 앱·실행기를 사용하여 HTTP API, 공개 채팅 계약, 조회 가능한 상태/이력으로 검증. 브라우저에서 핵심 연결을 확인 | 모듈마다 내부 전용 테스트 API 추가, DB·실행기를 모두 모킹한 정상 흐름 |
| 보조 경계: 독립 매칭 정답 비교 | 정해진 입력과 결과 계약으로 작은 후보군의 독립 탐색 결과·필수조건과 비교 | 실제 매칭 구현을 그대로 가져온 기대값, 점수·목적함수 미정 상태의 최적해 주장 |

제품 외부 행동을 주 경계로 하고 작은 데이터 매칭 정답 비교를 보조 경계로 삼는 안은 사용자 답변 “제안한 검증 경계로 진행”으로 확인했다. 실패·시간 제어의 구체 도구·계약은 후속 결정이다. 단위·통합·E2E 도구와 실제 시간 제어 방식은 아직 선택하지 않았다.

### 4. PRD 12단계 E2E 인수 기준

| 단계 | 배포 환경에서 확인할 결과 |
|---|---|
| 1 | 서로 다른 테스트 프로필로 날짜·지역 선택과 신청을 완료한다. |
| 2 | 마감 시각에 결제 완료자만 자동 매칭된다. |
| 3 | 필수조건과 우선순위에 따라 4~6인 테이블이 생성된다. |
| 4 | 미완성/부적합 조합이 해제되고 적합한 미확정 테이블로 재배치된다. |
| 5 | 최종 검증 후 운영자 승인 없이 자동 확정된다. |
| 6 | 적합한 가상 식당과 앱 단체방이 자동 배정·생성된다. |
| 7 | 참가자가 방에서 결과·식당·큐레이션·안내를 확인한다. |
| 8 | 미매칭 참가자가 대안 및 이동/환불을 선택하고 자동 처리 결과를 확인한다. 보관 선택도 별도 P0로 검증한다. |
| 9 | 하루 전 리마인드와 행사 중 콘텐츠가 자동 게시된다. |
| 10 | 참가자 체크인과 만족도·사람별 선호를 기록한다. 체크인 시점은 미결정 충돌을 해소한 기준으로 검증한다. |
| 11 | 다음 매칭에 이전 만남과 피드백이 반영된다. |
| 12 | 정상 흐름은 운영자 개입 없이 끝나고 미해결 예외만 어드민에 남는다. |

데모는 성공·재배치·실패·이동·보관·환불·식당 부족·알림 실패·피드백 반영을 재현할 데이터를 구분한다. 심사위원용 참가자·운영자 계정과 링크를 제공하며 결과 안내까지 접속 가능 상태를 유지한다.

## Out of Scope (범위 제외)

- 이번 문서/티켓 작성 Task에서 제품 코드, 인프라 생성, 과금, 실제 배포를 수행하는 일.
- 네이티브 앱·별도 SSR 화면 서버·마이크로서비스 확장, 여러 배포 플랫폼 도입.
- 실제 PG·실제 정기 청구·실제 금융 환불, 외부 식당 예약 API.
- 현행 폼 3회권을 별도 필수 상품으로 추가하는 일.
- LLM 궁합 판정, 결과에 따라 자동으로 가중치를 학습하는 P2 추천.
- 증거 없는 MBTI 궁합의 과학적 효능 주장, 모든 입력의 전역 최적해·임의 규모 성능 보장.
- Blaybus 자동 동기화 시스템을 별도 개발하는 일, 실제 시간을 추정해 입력하는 일.
- 원본 데이터의 무단 덮어쓰기·개인 식별 추정·원본 자료 공개. 로고 유사 재현은 공식 FAQ 허용 범위에서 수행한다.

P1/P2라는 이유로 본문과 충돌한 요구를 자동 삭제하지 않는다. 특히 확정 후 취소 충원/재배치와 최소점수 설정의 P0 해석은 아래에 남긴다. 회원/이용권 조회 등 P0를 동작시키는 최소 처리는 P1 화면의 범위 제외와 구분한다.

2026-10-16 사용자 승인·등록에 따라 기존 Agenda 5개를 유지하고 공통 설계 Work 1개·Task 3개와 데이터 Work의 시드 Task 1개를 추가했다. [승인된 배치](./design-readiness-plan.md)를 따른다. 공통 설계는 핵심 관계·상태·무결성, 공통 UI/전체 흐름, 공개/권한·검증 기준을 정하며 세부 스키마·화면은 각 기능에서 보완한다. 초기 전체 스키마 동결이나 미결정 정책의 일괄 확정이 아니다.

인증·권한·예외 처리·화면 설계와 검증은 각 기능 Task에서 함께 완성한다. 마지막 Work까지 미루지 않는다. Work가 넓어 새 Task가 필요하면 등록 구조·추가 이유·완료 기준·일정 영향을 사용자에게 먼저 제시한다.

### 3. 본 문서 Task의 완료 기준

- 확정 기술과 대체된 추천안을 구분한다.
- PRD P0 및 12단계 E2E와 구현·검증 목표를 연결한다.
- 미결정 정책·계약·도구를 명시하고 승인되지 않은 숫자/알고리즘을 확정값으로 넣지 않는다.
- 테스트 경계를 사용자에게 확인하고 응답을 반영한다.
- 문서와 근거를 검토 가능한 PR로 제공하고 해당 Task 기록란에 붙일 실제 링크·수행·검증 문구를 제공한다.
- 본 Task 완료와 전체 Work·제품 구현 완료를 구분한다. Work Issue는 다른 하위 Task 및 인수 기준도 충족하기 전 닫지 않는다.

### 4. 근거와 문서 관리

공식 PRD v0.2의 §6~§18을 요구사항 근거로 삼는다. 사용자 제공 킥오프 Q&A와 실제 Google Forms는 운영 현황 참고이며 충돌 시 자동으로 PRD를 덮어쓰지 않는다. 승인된 ADR-0002~0007, 도메인 용어집, 설계 인터뷰, 폼/데이터 검토 기록과 사용자 최신 지시를 구현 방향의 근거로 사용한다.

이 명세는 문서 작성 Task의 결과물이다. 기존 설계 기록과 원본 자료는 보존하며 원본 엑셀·이미지·PDF를 이번 문서 PR에 포함하지 않는다. GitHub Issue와 PR을 만들었다는 사실만으로 구현이나 Blaybus 반영을 완료 처리하지 않는다.
