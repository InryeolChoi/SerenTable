# CI 실행 시간 개선

위치: 개발·배포 기반 확보 → 첫 배포·CI·DB 연결(#2) → DB 연결과 CI 구성의 유지보수. 새 Work/Task를 만들지 않는다. 제출 검증(#10)의 기존 필수 범위도 유지한다.

## 기준과 변경

기준 커밋: main `01deb3f`(PR49). 기존 CI 39251409277은 20분 17초, 그중 pytest 17분 43초, 브라우저 1분 15초, 이미지 15초, 복원 21초였다. 설치 캐시보다 순차 pytest가 주 병목이다.

- Python 시험: 전체 수집 후 파일별 테스트 수가 큰 순으로 가장 적게 배정된 묶음에 배분한다. 네 backend 실행기는 각자 다른 runner/PG17 서비스 컨테이너를 사용한다. 파일 안의 시험 순서와 모듈 fixture 경계는 유지한다.
- 브라우저: 별도 runner/PG17에서 기존15개 E2E를 그대로 실행한다. DB 초기화를 backend와 공유하지 않는다.
- 이미지/PG18복원: 별도 runner에서 기존 검증을 그대로 수행한다.
- `verify`: 세 종류의 작업이 전부 success여야 성공한다. 실패·취소·skip은 성공으로 해석하지 않는다. 기존 필수 검사 이름을 보존하지만 Railway 설정이나 브랜치 보호를 직접 수정하지 않는다.
- `--durations=25`와 분할별 JUnit artifact(7일보관)로 다음 개선에 사용할 시험별 시간을 수집한다. 제품 코드·정책·운영 DB·배포 설정은 바꾸지 않는다.

## 검증

전체 수집 366개(기존 363개 + 신규 분할 검증 3개)를 92/92/91/91개로 나눠 합집합 일치·중복 0을 확인했다. 분할의 결정성·모듈 경계·잘못된 분할 수 거절 시험 3개가 통과했다. 실제 집계 shell에서 success만 통과하고 failure/cancelled/skipped는 실패하는 것을 확인했다. YAML 구문 파싱·Ruff·형식·diff 검사를 통과했다.

실제 PostgreSQL 17 전용 컨테이너 `serentable-ci-speed-pg`의 ci_shard_1~4에서 병렬 전체 검증을 진행한다. 운영이나 Claude의 로컬 DB를 사용하지 않는다. 결과와 실제 GitHub CI 소요 시간은 아래 후속 기록 및 PR 체크를 기준으로 한다. 로컬과 GitHub의 하드웨어가 다르므로 서로의 시간을 동일 환경 비교처럼 표시하지 않는다.

## 위험과 후속

- 테스트 수 균등화는 실행 시간 균등화를 보장하지 않는다. 새 시간 자료로 후속 조정한다.
- 여러 runner의 실행 시간 합/사용량은 늘 수 있다. GitHub 동시실행 한도로 대기할 수 있다.
- 전역 DB 정리 fixture가 있으므로 동일 DB pytest-xdist 병렬화는 적용하지 않는다.
- 순차 전체만 통과하는 시험 간 숨은 의존성이 드러나면 격리 결함을 수정해야 하며 검증을 삭제하지 않는다.
- main 병합은 Railway 자동 배포를 유발할 수 있으므로 사용자에게 맡긴다.

## 로컬 검증 결과

2026-10-19 로컬 PG17 독립 DB 네 개에서 **366개 전체 통과**, failure/error/skip은 0이었다. 분할별 시간은 157.98 / 348.31 / 145.13 / 216.13초이며, 병렬 실행 전체는 350.4초(5분 50초)였다. 가장 느린 묶음에는 합성 100명의 HTTP 시나리오가 포함되어 있다. 파일 수·시험 수만으로 실행 시간을 완전히 균등화할 수 없음을 확인했다.

이 수치를 GitHub의 기존 20분 17초와 같은 환경의 전후 비교로 표시하지 않는다. 새 GitHub CI의 결과는 PR Checks에서 별도로 확인한다. 호스트 화면 빌드는 Node26으로 통과했으며, 기준 Node22의 브라우저·빌드 및 Linux 이미지/복원 실행은 새 CI에서 확인한다.
