## 승인된 정책

사용자가 이번 인터뷰에서 세 항목을 승인했다. 실패한 미사용 1회권은 현재 후보를 닫고 만료 없이 보관하며 새 신청에 재사용할 수 있다. 시스템 최종 매칭 실패의 미사용 1회권은 일반 취소 시간 제한과 무관하게 원금 전액을 자동 **모의 환불**한다. 실제 PG 취소·일반 취소·부분 환불은 포함하지 않는다. 멤버십은 신청의 모든 적격 후보가 최종 실패했을 때 기존 만료 시각에 7일을 신청당 한 번 더한다. 같은 신청의 대안 이동·재시도로 중복 연장하지 않는다. 멤버십 금액 환불은 보류한다. MBTI 가중치는 ADR-0011을 유지하고 최소 50은 개발 후보일 뿐 운영 승인값이 아니다.

## 계약 세부

- 해결은 SUBMITTED, ALTERNATIVE_OFFERED 또는 겹침 확정 사유가 아닌 legacy NO_MATCH, 살아 있는 확정 없음, 적격 기존 후보의 성공 실행이 모두 끝난 때만 허용한다. 기술 오류는 미매칭으로 환불하지 않는다.
- 대상은 모집 중이며 성공 실행 없음, 본인 다른 신청의 live 후보 아님, 다른 확정과 시간 겹침 없음, 현재 이용권으로 자격 충족해야 한다. 목록 조회와 선택 시 동일 조건을 재검사한다. 원래 선택 밖 날짜·지역 이동은 참가자의 명시적 선택만 허용한다. 확정 테이블은 변경하지 않는다.
- 기존 선택 후보는 기존 Worker의 매칭 시각 순으로 계속 처리한다. #39의 후보 순서/자동 매칭 엔진을 새 엔진으로 대체하지 않는다. PRD §7.4의 날짜·지역별 상대 우선순위와의 차이는 사용자가 기존 매칭 시각순을 유지하는 명시적 MVP 예외로 승인했다.
- 원신청 submitted_at은 구매·제출 역사로 보존한다. 이동 동의 시각은 별도 이력에 보존하며 기존 신청 제출 시각순 계약을 유지한다.
- 동일 요청 키와 같은 입력은 마감·현재 상태 변화 뒤에도 동일 해결 결과를 반환한다. 같은 키의 다른 입력·같은 실패의 다른 선택은 409. 해결 기록·후보 변경·권리 변경은 하나의 트랜잭션이며 오류 시 전부 롤백한다.
- 보관 재사용은 원 payment.application_id·entitlement.application_id를 바꾸지 않고 별도 권리 예약 이력을 추가한다. 사용 이력이 있는 권리는 되살리지 않는다.
- 변경 전 0009까지와 이후 0010을 구분한다. 운영 migration/deploy/seed/match/write는 실행하지 않는다.

## 실제 API·스키마 대응

- `GET /api/me/applications/{id}/alternatives`: 기존 두 목록에 `failure_run_id` 추가. 보유 권리·기한·모집/성공 실행·기존 확정 시간 겹침을 확인한 회차만 제안한다. 조회는 선택·거래를 변경하지 않는다.
- `POST /api/me/applications/{id}/resolutions`: `{request_key, failure_run_id, action: TRANSFER|HOLD|REFUND, event_slot_id: UUID|null}`. 성공 200과 고정 해결 결과. TRANSFER만 대상 필수, 그 외 대상 금지. 동일 입력 재전송 200, 키 재사용/상태 경합/부적격 대상/멤버십 환불 409, 입력 422, 타인 404, 운영자/CSRF 403, 비로그인 401, 저장 오류 503. 오류에서 개인 조건·다른 사용자 정보를 반환하지 않는다.
- `POST /api/me/entitlements/{id}/reuse`: `{request_key, application_id}`. 명시 보관된 미사용 PAID SINGLE을 모집 중 신규 신청에 연결한다. 별도 결제 생성 없음. 기존 멤버십/권리가 이미 있거나 마감·중복/사용된 권리는 거부. 재전송은 원래 예약 결과를 반환한다.
- 기존 본인/운영자 신청 조회에 `resolutions`, 후보의 `live`·`source_resolution_id` 추가. 이용권 조회에 `reserved_application_id`·`reusable`, 환불된 이용권/결제에 `REFUNDED` 추가. `application_id`는 원구매 참조로 계속 유지한다.
- 마이그레이션 `0010_match_resolution`(선행 `0009_matching_score`)만 추가한다. 상세 물리 구조·그림은 [데이터 모델](./core-data-model.md)의 최신 절을 따른다. 새 API와 기존 Worker 스케줄·점수 함수는 동일하며 기존 엔진을 교체하지 않는다.

## 운영 반영 전 조건과 남은 범위

1. 현재 작업은 로컬·격리 시험 DB에서만 진행했다. 사용자 별도 승인 전 PR #39/후속 구현을 main에 머지하거나 Railway 배포하지 않는다. 재확인 결과 문서 PR #38은 이미 MERGED이며 에이전트가 머지한 것이 아니다. main 변경으로 자동 배포될 수 있으나 이번 작업에서 운영 배포 상태는 조회·변경하지 않았다.
2. 이후 승인하더라도 새 백업·복원 가능 확인 후 API 쓰기와 기존 worker를 중지한 유지보수 창에서 0009→0010을 적용하고 새 API/worker를 함께 시작해야 한다. 구형 API는 새 SINGLE의 binding을 만들지 않고 구형 worker는 새 예약/공통 잠금을 모르므로 혼합 버전 운영을 허용하지 않는다. 실제 실행 명령/중단 순서는 운영 승인 단계에서 확정한다.
3. 0010은 기존 SINGLE 예약만 보충하며 이미 성공한 운영 매칭을 재실행하거나 확정 테이블/원결제를 바꾸지 않는다. 과거 멤버십 실패를 운영에서 일괄 소급 연장하지 않는다. 환불된 데이터가 있을 때 downgrade를 실행하면 제약으로 거부된다. 전방 수정/백업 복구를 검토해야 한다.
4. 최소 매칭 점수 50은 개발 후보이며 운영 승인값은 미정이다. MBTI 가중치는 사용자 요청대로 유지했다.
5. 사용자는 기존 U07 매칭 시각순을 유지하고 PRD §7.4의 날짜·지역별 상대 우선순위와의 차이를 **명시적 MVP 예외로 승인**했다. 동의한 기존 후보를 기존 Worker가 계속 처리하고, 범위 밖 회차는 명시 선택 후 이동한다. 정책 결정 대기는 해소됐으나 PRD 상대 우선순위까지 구현했다고 표시하지 않는다.
6. 멤버십 금액 환불·일반 취소/노쇼 정책, 식당·채팅·알림(Work #7), 참석·피드백·다음 추천(Work #8), 운영자 예외·안전 종합(Work #9), 통합 시연·제출(Work #10)은 별도 미완료다. Work #6/Agenda 전체 완료·운영 인수 완료로 표시하지 않는다.

### PAY-01 최종 조회 보완

`refund_state=REFUND_AVAILABLE`을 해결 가능 시 본인·운영자 신청 조회와 본인 대안 조회에 표시한다. 원결제 PAID와 별도 파생 축이므로 적격 판정의 원금 상태를 바꾸지 않는다. `resolutions[].refund_events`에 모의 요청→처리→완료의 금액·시각을 제공하고, 동일한 이력을 참가자/운영자 화면에서 확인한다. 실제 처리기는 한 트랜잭션에 즉시 완료하며 비동기 PG를 흉내 내는 장기 처리 중 상태는 만들지 않는다. 이 조회 보완의 RED를 확인한 뒤 관련 API20 PASS(69.10초), Node22 전체 브라우저10 PASS(35.3초), lint/format·타입/빌드 PASS. 앞의 전체224 PASS는 이 조회 보완 전 제품 코드이며 최종 head 전체 회귀는 PR #40 CI에서 확인한다.
