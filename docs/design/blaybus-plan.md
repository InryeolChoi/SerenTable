# Blaybus Workspace 구조와 운영 기록

## 확정된 계층과 운영 방식

사용자 Q16/Q17 답변에 따라 기능·성과별 Agenda와 Issue 없는 교차 링크 운영은 확정했다. Agenda 안에 Work가 있고 각 Work 안에 Task가 있다. 아래 항목별 상세 분할은 등록 초안이며 이전 날짜별 일정표는 참고 계획이다. 사용자가 전체 트리를 Blaybus에 등록했다고 보고했다. 실제 UI와 항목별 URL/상태는 아직 확인하지 않았다.

| Agenda | Work 초안 | 완료 증거 예시 |
|---|---|---|
| 1. 개발·배포 기반 | 설계·명세와 저장소 정리 / 최초 배포·CI·DB 연결 | ADR, PR, CI, 배포 URL |
| 2. 참가 신청·이용권·결제 | 로그인·프로필·동의 / 복수 일정 신청·모의 결제·이용권 | 정상/필수값 누락/권한 검증 |
| 3. 자동 매칭·실패 해결 | 매칭 규칙·독립 정답 비교 / 예약 실행·재배치·확정 / 일정 이동·보관·환불 | 필수조건 검사, 매칭 이력, 중복·복구 검증 |
| 4. 모임 안내·피드백·재방문 | 식당·채팅·푸시·예약 콘텐츠 / 참석·피드백·신고·다음 추천 | 참가자 E2E, 발송·재시도 결과, 다음 매칭 반영 |
| 5. 운영자 예외·최종 검증·제출 | 예외·안전 어드민 / 12단계 E2E·100명·장애 검증 / 제출·가용성 | 예외 처리 이력, 검증 결과, 계정·링크 |

어드민·권한·실패 검증은 각 기능 Work와 함께 구현하며 마지막 Agenda까지 전부 미루는 뜻이 아니다. 마지막 Agenda는 예외 종합 화면 및 통합 검증이다. 채팅과 알림 등의 구체 설계는 해당 Work의 선행 Task에 남긴다.

예시 Work: `최초 배포·CI·DB 연결`

1. Task: 최초 배포 명세와 완료 기준 확정.
2. Task: React/Vite·FastAPI·DB 연결 골격 구성.
3. Task: CI 성공 후 Railway 배포 흐름 구성.
4. Task: 모바일 화면·API·DB 연결 검증 및 증거 기록.

각 Task 설명은 `목적 / 선행 조건 / 완료 기준 / PRD 근거(해당 시) / GitHub 증거 링크 / 예상·실제 시간`을 사용한다. Work와 Task의 식별자는 UI의 실제 식별자를 확인해 연결하고, 임의로 실제 플랫폼 ID인 것처럼 생성하지 않는다.

### GitHub와 연결하는 확정 운영 방식

- Blaybus: 목표일, Task 진행, 실제 투입 시간과 작업 요약을 기록한다.
- GitHub: 설계·코드·PR 리뷰·CI 검증 근거를 보관한다.
- 연결: Task 설명에 해당 PR/CI/문서 링크를 넣고, PR 설명에 Blaybus Task 링크를 넣는다. Task 여러 개가 하나의 PR로 끝나면 같은 PR 링크를 사용해도 되며 1:1 관계를 강제하지 않는다.
- 완료: 코드 작성만이 아니라 합의한 검사·배포 확인까지 끝난 Task만 완료로 기록한다. CI 통과를 곧바로 제품 기능 완료로 간주하지 않는다.
- Dashboard: 세션 종료 시 Work 완료/미완료와 시간 편중을 점검하고 다음 Task를 조정한다. 자동 집계 항목은 실제 UI 확인 후 사용한다.
- 기본 추천은 GitHub Issue를 추가하지 않는 것이다. 기존 Issue 생성 금지는 유지한다. 사용자가 Work 단위 Issue 추적을 원하면 별도 선택으로 바꿀 수 있다.

공개 사실 확인: [Blaybus 공식 홈페이지](https://www.blaybus.com/)와 [공식 Work 소개](https://work.develop.blaybus.com/)에서 계층형 작업·시간/진행 기록을 확인했다. 전용 플러그인 검색은 결과 없음. 공개 자료에서 GitHub 동기화/API/webhook/MCP 지원은 확인하지 못했으며 지원 불가로 단정하지 않는다. 로그인 UI를 아직 보지 않았고 실제 Task URL 형식도 미확인이다. 자동 연동 개발을 핵심 일정에 추가하지 않는다.

GitHub 상태 재확인: `InryeolChoi/SerenTable`, 비공개, 기본 브랜치 `main`, 원격 커밋 `ab7c6ceb4851ef686369daa8bbc1ec7675b4e464`. 이후 설계 문서 변경과 추가 파일은 로컬에 남아 있다. 새로 발견한 `data/`는 이번 요청 범위에서 읽거나 업로드하지 않는다.

아래는 등록 전 작성했던 일정 초안이다. 이후 사용자가 전체 트리의 수동 등록 완료를 보고했다. 사용자 시간대 Asia/Seoul 기준으로 10/15는 준비, 10/16부터 본격 구현, 10/20 개발 완료 목표, 10/21 23:59 제출이다. 실제 가용 시간은 미확인이며 내일 3시간을 가정한다. 예상 시간은 실제 투입 시간으로 기록하지 않는다.

## 계획과 이미 한 작업의 구분

- 오늘 한 PRD/자료 검토, 설계 인터뷰, GitHub 저장소 생성은 준비 작업으로 기록한다. 실제 수행일은 10/15 및 해당 대화의 실제 날짜를 사용하고 10/16에 수행한 것처럼 기록하지 않는다.
- 설계 결정은 구현 완료가 아니다. 화면·API·테스트·배포는 아직 미구현이다.
- 내일 Workspace에 오늘까지의 준비 결과와 문서 링크를 등록할 수 있다. 등록일과 실제 수행일을 구분한다. 오늘 작업의 시간은 사용자 확인 없이 추정해서 채우지 않는다.
- 공개된 배포 링크가 없으므로 Output에 배포 완료라고 기록하지 않는다. 오늘의 실제 산출물은 GitHub 저장소와 설계 문서다.
- Dashboard는 사용 가능한 완료율/투입 시간 지표를 보고 다음 세션의 작업을 조정하는 데 쓴다. 아직 실제 화면을 확인하지 않았으므로 특정 필드/자동 연결 기능이 있다고 가정하지 않는다.

## 프로젝트 목표

PRD P0와 §18의 12단계 E2E를 만족하는 심사용 소셜다이닝 MVP를 10/20까지 완성하고 10/21 제출한다. 운영 자동화의 중복 실행 방지·트랜잭션·재시도·복구를 검증하며, 매칭은 필수조건 및 작은 데이터 정답 비교를 확보한다.

## 10/16 Agenda: 개발·배포 기반 확보

**당일 완료 목표**: GitHub의 한 변경을 기본 CI 검사 후 Railway에 배포하고, 모바일 브라우저에서 참가자/운영자 경로에 접근하며 FastAPI가 PostgreSQL에 연결하는 것을 확인한다. 이는 P0 기능 구현 완료가 아닌 첫 운영 경로의 확보다.

### Work 1. Workspace 계획과 최초 작업 명세 정리 — 25분

| Task | 예상 | 완료 기준 |
|---|---:|---|
| 준비 결과·미결정 목록 등록 | 10분 | GitHub/ADR/인터뷰 링크와 오늘까지 실제 한 작업을 구분해 기록 |
| 최초 배포 Work 명세 확인 | 15분 | 앱/DB/실행기 책임, CI→배포 조건, 비밀값 취급, 첫 검증 항목이 명확하며 구현 시작을 사용자가 승인 |

매칭 점수·구독 정책 등 미결정 내용은 해당 기능 Work의 선행 Task로 둔다. 전체 제품 명세가 완료되었다고 선언하지 않으며 최초 배포의 좁은 명세만 먼저 정할 수 있다. 코드 작성 금지는 사용자가 내일 구현 시작을 지시할 때까지 유지한다.

### Work 2. 최소 프로젝트와 자동 검사 구축 — 60분

| Task | 예상 | 완료 기준 |
|---|---:|---|
| React/Vite 화면·FastAPI 앱 골격 | 30분 | 로컬에서 화면 빌드 및 API 응답 확인. 참가자/어드민 경로는 임시 골격으로 표시하며 권한 구현 완료로 간주하지 않음 |
| DB 연결·기본 마이그레이션 구성 | 15분 | PostgreSQL 연결을 확인하고 변경 이력을 관리할 시작점 확보 |
| GitHub Actions 기본 검사 | 15분 | 프론트 타입/빌드, 서버 기본 검사 및 의미 있는 최소 스모크 검증 성공. 업무 정확성 테스트와 구분 |

### Work 3. Railway 최초 배포 — 75분

| Task | 예상 | 완료 기준 |
|---|---:|---|
| Railway 프로젝트·앱·PostgreSQL 준비 | 20분 | 계정/요금·비용 한도와 설정을 확인한 뒤 승인된 자원을 생성. DB 영속 저장 설정 확인 |
| 빌드·환경변수·배포 연결 | 35분 | 비밀값은 저장소 밖에 설정. 화면 파일과 API 배포 성공. 실패한 CI에서 배포가 시작되지 않는 연결 확인 |
| 배포 검증 및 자원 사용 확인 | 20분 | 모바일 접속·새로고침·API 응답·DB 연결 확인. 배포 SHA, 로그와 초기 사용량 기록 |

작업 실행기의 별도 실행은 확정된 방향이다. 첫날에는 실제 매칭/알림 로직 없이 실행 시작·종료·DB 연결 확인을 여유가 있을 때 추가하며, 해당 작업이 끝나지 않으면 Work를 완료 처리하지 않고 10/17 첫 작업으로 명시한다.

### Work 4. 결과 기록과 다음 세션 준비 — 20분

| Task | 예상 | 완료 기준 |

**합계: 180분.** 새 계정 설정·결제/배포 문제로 초과하면 기능 구현을 추가하지 않고 미완료 원인과 다음 Task를 기록한다. 시간이 남으면 로그인 범위와 인증 라이브러리 선택을 정리한다. 프로필/매칭/채팅까지 첫날 완료한다고 약속하지 않는다.

특히 10/18에 충분한 구현 시간이 있다는 전제를 두지 않는다. 마지막 날까지 기능을 미루지 않으려면 후속 명세에서 각 Task를 작게 나누고 자동 구현과 독립 검증의 작업량·가능 시간을 확인해야 한다. 심사 기간 배포 유지와 백업/복원 확인도 제출 Work에 포함한다.

## 기능 Work를 작성하는 공통 형식

- 목표: 참가자 또는 운영자에게 생기는 확인 가능한 결과.
- PRD 근거: 요구사항 ID와 E2E 단계.
- 선행 Task: 미결정 정책, 필요한 데이터/권한.
- 구현 Task 및 검증 Task: 서로 구분.
- 완료 기준: 정상/실패 동작, 테스트 결과, 배포 확인.
- 증거: 문서·PR·CI·테스트 출력·배포 URL.
- 기록: 예상 시간과 실제 시간 분리, 미완료 이유와 다음 행동.

```text
│  ├─ Task: 가상데이터 변환·DB 시드 구축
│  ├─ Task: 100명 실행 사례와 작은 정답 사례 준비
│  └─ Task: 매칭 점수·제외 조건 기준 확정
└─ Work 2. 예약 매칭·재배치·실패 해결
   ├─ Task: 자동 실행·확정·대안·이동/환불 구현
   └─ Task: 필수조건·중복·중단 복구 검증

Agenda 4. 모임 안내·피드백·재방문
├─ Work 1. 식당·채팅·알림
│  ├─ Task: 제공 브랜드 자료 적용
│  ├─ Task: 배정·단체방·예약 메시지 구현
│  └─ Task: 접근 권한·발송 실패 재시도 검증
└─ Work 2. 참석·피드백·다음 추천
   ├─ Task: 체크인·선호·신고·추천 구현
   └─ Task: 다음 매칭 반영 검증

Agenda 5. 운영자 예외·최종 검증·제출
├─ Work 1. 운영자 예외·안전 종합 관리
│  ├─ Task: 기능별 예외·조치 연결
│  └─ Task: 권한·처리 이력 검증
└─ Work 2. 통합 검증·제출
   ├─ Task: 12단계 E2E·100명·복구 검증
   └─ Task: 테스트 계정·배포 링크·증거 제출 준비
```

같은 이름의 Task도 소속 Work에 따라 목적이 다르며 실제 등록 시 제목과 완료 기준을 구체화한다. 준비 작업 중 이미 한 것은 실제 수행일·증거에 맞춰 기록하고 구현 Task와 섞지 않는다. 브랜드 자료 적용은 제품 화면 작업에 속하며 실제 등록 시 프론트 담당 Work로 조정할 수 있다.


## 수동 갱신 안내 규칙 — 사용자 확정 지시

사용자가 전체 트리를 등록했다고 보고했고, 직접 Blaybus를 수정해야 한다고 설명했다. 앞으로 의미 있는 작업을 완료한 응답에는 사용자가 수행할 갱신을 반드시 안내한다. 항목별 실제 URL/ID는 아직 미확인이므로 문서상의 Agenda/Work/Task 경로를 사용하고 확인되지 않은 ID를 만들지 않는다.

- Task: `Agenda > Work > Task` 경로, 붙여 넣을 수행 내용, 완료/진행 중/차단 등 제안 상태, 검증 근거 링크를 제공한다. 실제 투입 시간은 사용자가 확인한 시간만 기록하며 AI 실행 시간을 사용자 작업 시간으로 추정하지 않는다.
- Work: 하위 필수 Task와 합의한 완료 기준이 충족된 경우에만 완료로 바꿔달라고 요청한다. 한 PR/CI 완료만으로 Work 전체를 완료 처리하지 않는다.
- Agenda: 범위·목표·일정·선행 관계가 실제로 바뀌었을 때 바꿀 항목과 변경 전후를 적어 수정해달라고 요청한다. 매번 Agenda를 수정하라고 하지 않는다.
- 사용자가 실제 수정했다고 응답하기 전에는 Blaybus 반영 완료로 기록하지 않는다. 수정 요청을 준 사실과 사용자 완료 보고를 구분한다.
- 같은 작업의 중간 도구 호출마다 요청하지 않고 완료 결과 보고에서 해당 변경을 모아 제공한다. 새 질문의 추천만으로 구현 Task를 완료로 처리하지 않는다.

복사 안내 형식:

```text
Blaybus 수정 요청
위치: [Agenda] > [Work] > [Task]
상태: [완료/진행 중/차단]
기록: [실제 수행한 내용]
검증/증거: [테스트 결과·PR·문서 등]
Work: [완료 조건 충족 시에만 완료 요청]
Agenda: [변경 필요 시에만 구체 수정 요청]
```

Issue 매핑은 사용자가 재논의를 요청했다. 기존 Issue 없는 운영은 확정 변경 전까지 유지한다. 최신 추천은 Work 1개를 Issue 1개로 추적하고 Task는 체크리스트/연결 PR로 추적하는 안이다. 아직 사용자 선택·Issue 생성은 하지 않았다.

PR과 Task는 강제 1:1 관계를 두지 않는 것을 추천한다. PR은 함께 검토·병합할 변경 단위다. 구현과 테스트 Task를 한 PR로 묶을 수 있고 자료 확인·배포 검증 Task는 새 PR 없이 증거를 남길 수 있다. 각 PR이 관련 Task를 명시하고, Work Issue는 하위 작업과 인수 조건이 모두 완료될 때 닫는 안이다. 이 원칙은 아직 선택 대기 중이다.

## 최신 확정: Work당 Issue 하나, Task 기록란에 관련 PR 링크

사용자가 위 매핑을 승인했다. 앞선 ‘Issue 없이 운영’ 및 ‘선택 대기’ 문구는 이전 논의 이력이며 현재 운영 원칙은 다음과 같다.

- Work 1개에 GitHub Issue 1개를 연결한다. Issue 생성 시 해당 Work의 목적·Task 체크리스트·완료 기준을 담는다. 실제 생성 범위/순서는 실행할 Work에 맞춰 정하며 이번 승인만으로 모든 Issue를 생성했다고 기록하지 않는다.
- Task와 PR은 강제 1:1이 아니다. Task 완료 시 관련 PR 링크와 수행·검증 내용을 해당 Task의 작업 내용 기록란에 남긴다. 같은 PR이 여러 Task를 충족하면 같은 링크를 각각 사용한다.
- PR이 없는 자료 확인/실행 검증 Task는 존재하지 않는 PR을 만들거나 링크를 추정하지 않는다. 관련 문서/커밋/CI 등 실제 증거를 안내하고 아직 PR이 없으면 그 사실을 밝힌다. PR이 생성되면 실제 URL로 안내한다.
- 사용자 스크린샷에서 Task 상세에 파일 첨부용 ‘중간 산출물’ 영역과 ‘이 태스크에서 수행할 작업 내용을 기록하세요’ 텍스트 영역(2,000자 표시)을 확인했다. PR URL은 후자의 작업 기록에 붙여 넣도록 안내한다. URL 전용 첨부 기능이 있다고 가정하지 않는다.
- 완료 기준 충족 여부와 PR 병합 상태를 구분한다. 구현 Task의 관련 PR은 열린 상태/병합 상태와 검증 결과를 밝히고 합의한 완료 기준에 따라 상태를 요청한다. 중간 PR이 Work Issue 전체를 조기 종료하지 않도록 한다.
- Blaybus는 사용자가 수동 수정한다. AI는 정확한 Agenda > Work > Task 경로와 복사할 기록, 제안 상태를 제공한다. 사용자에게 반영 확인을 받기 전에는 외부 갱신 완료로 기록하지 않는다.

복사 형식:

```text
수행 내용: ...
검증 결과: ...
관련 PR: 실제 PR URL (상태: 열림/병합)
추가 증거: 문서/CI 등 필요한 실제 링크
남은 작업: 없음 또는 구체 항목
```

사용자 스크린샷에서 확인한 정확한 첫 경로는 `개발·배포 기반 확보 > 요구사항·설계·자료 정리 > PRD·구글폼·킥오프 차이 기록`이다. 같은 Work 아래 `가상데이터 구조와 누락값 확인`, `기술 결정 및 미결정 항목 정리` Task가 보인다. 앞으로 해당 항목은 이 이름을 사용한다. 전체 UI 상태나 실제 Task URL은 아직 확인하지 않았다.

## 기본 작업 순서와 추가 항목 안내

- 사용자가 확정한 Agenda → Work → Task 순서로 진행한다. 현재 Task는 `개발·배포 기반 확보 > 요구사항·설계·자료 정리 > 기술 결정 및 미결정 항목 정리`이다.
- Work·Task 추가가 필요하면 이유, 들어갈 계층, 완료 기준, 일정/의존성 영향을 먼저 제시하고 사용자가 Blaybus에 반영할 문구를 제공한다. 추가 항목을 임의로 등록하지 않는다.
- 현재 Task의 산출물은 구현 명세서와 그 검토용 PR이다. 구현 명세서에는 확정 사항, 미결정 정책, 검증 경계, 이후 Work·Task 완료 기준을 구분한다.
- [구현 명세서](./mvp-implementation-spec.md)와 [Issue 발행 계획](./github-ticket-plan.md)을 준비했다. `to-spec`의 검증 경계와 `to-tickets`의 Work 10개 분할·의존성은 사용자 확인을 받았다. 이 기준으로 발행하고 진행 중 수정 사항을 먼저 안내한다. 문서 검토용 PR을 준비하는 동안 이후 제품 구현 Task는 시작하지 않는다.


## 2026-10-15 실제 등록 구조 갱신

사용자가 제공한 23:26 화면의 네 완료 Task와, 이어서 추가했다고 확인한 `배포 안전장치·원격 작업 검증`을 위 트리에 반영했다. Work `첫 배포·CI·DB 연결`은 진행 중이다. 화면의 네 완료 Task는 최신 사용자 상태를 따른다. 제품 기능이나 모든 브라우저 조합의 검증 완료를 의미하지 않는다.

추가 Task는 기존 Work의 남은 인수 조건을 추적하기 위한 분리이며 별도 Work/Issue를 만들지 않는다. 완료 기준은 API·worker의 Wait for CI 설정과 실패 차단 증거, 비용 알림/상한 확인, Railway 백업·복원 준비 확인, 모바일 Codex 지시→PR→CI의 실제 수행 근거다. 자격 증명은 채팅/문서에 기록하지 않는다. 외부 설정·기기 접근에 따라 30~60분을 예상하며 실제 시간은 사용자가 기록한다.

다음 실행 순서는 CI 배포 차단 → 비용/백업 준비 → 모바일 원격 작업이다. 초기 설정 조회에서는 두 서비스 모두 `source.checkSuites=false`였으나 이후 활성화·실패 차단·정상 배포·main 복구를 검증했다([실제 기록](../operations/ci-gate-verification.md)). 다음은 비용/백업 준비와 모바일 원격 작업이다. 다섯 번째 Task 인수 조건까지 충족한 뒤 Work를 완료 처리하고 다음 Agenda의 `로그인·프로필·동의`로 진행한다.


## 2026-10-16 공통 설계·시드 등록 반영

사용자가 A안과 Work 1개·Task 4개 배치를 승인하고 등록 완료를 확인했다. 별도 Agenda 없이 `개발·배포 기반 확보`의 세 번째 Work로 공통 설계 Task 세 개를 추가했다. 실제 데이터 적재 Task는 `자동 매칭·실패 해결 > 규칙·데이터·정답 기준`에 추가했다. 기존 완료 Work/Task는 유지한다.

공통 설계 Work는 [대응 Issue](https://github.com/InryeolChoi/SerenTable/issues/15)에 연결한다. 기본 순서는 첫 배포 Work 마무리 → 핵심 ERD → 공통 UI/화면 흐름 → 개인정보·권한 기준 → 로그인·프로필·동의다. UI와 보안의 구체 구현/검증은 각 기능의 기존 Task 완료 기준에 포함한다. 상세 범위·일정은 [승인된 배치](./design-readiness-plan.md)를 따른다. 이번 반영은 등록 동기화이며 설계 산출물·DB 적재 완료가 아니다.
