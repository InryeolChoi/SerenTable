# GitHub Issue·PR 발행 계획

**상태:** 사용자 승인된 발행 기준안. 사용자 답변은 “일단 이렇게 하고, 해보면서 수정할까?”이다. 진행 중 변경이 필요하면 이유·완료 기준·일정 영향을 먼저 안내한다. 사용자가 등록한 Agenda → Work → Task 순서를 유지한다. Work당 Issue 하나, PR은 실제 산출물이 있는 Task의 검토 가능한 변경 묶음으로 만든다. 아직 구현하지 않은 Task의 빈 PR은 생성하지 않는다.

## 발행 및 실행 원칙

- 기존 Work 10개를 그대로 사용한다. 새 Agenda·Work·Task를 이번 계획에서 몰래 추가하지 않는다.
- 아래 식별자는 발행 전 순서 표기이며 실제 GitHub Issue 번호가 아니다.
- 기본 실행 순서는 1~10이다. ‘선행’은 실제 완료가 필요한 직접 의존성으로, 단순한 일정 순서와 구별한다. 선행이 적어도 임의로 다음 Agenda로 건너뛰지 않는다.
- Issue 본문에는 Blaybus 계층·목표·Task 체크리스트·인수 기준·정책 결정 전제·관련 명세·직접 선행 Issue를 기록한다.
- 선행 Issue 번호가 결정되면 GitHub의 지원되는 네이티브 차단 관계로 연결한다. 모든 Issue에 같은 내용을 반복한 상위 Issue를 별도로 만들지 않는다.
- `ready-for-agent`는 스킬에서 지정한 라벨이다. 선행/정책 전제가 남은 Issue는 해당 전제가 충족되기 전 착수하지 않는다. 라벨만으로 모든 제품 정책이 확정됐다고 해석하지 않는다.
- 현재 문서 PR은 1번 Work의 ‘기술 결정 및 미결정 항목 정리’ Task 결과물이다. 같은 Work의 앞선 자료 검토 결과를 근거로 포함한다. 전체 Work의 완료/종료는 별도 확인하며 자동 종료하지 않는다.
- 이후 PR은 관련 Issue를 참조하되 일부 Task만 끝난 PR에서 Work 전체가 자동 종료되지 않게 한다. 부모 Issue를 임의로 수정·종료하지 않는다.

## 1. 요구사항·설계·자료 정리

**위치:** 개발·배포 기반 확보 → 요구사항·설계·자료 정리

**선행:** 없음. 현재 작업.

**산출물:** PRD·현행 폼·킥오프 차이, 가상데이터 품질, 확정 기술·미결정 항목·검증 경계를 한 기준으로 검토할 수 있다. 제품 기능 대신 문서/검토 결과가 산출물인 준비 Work이다.

- [ ] PRD·구글폼·킥오프 차이 기록.
- [ ] 가상데이터 구조와 누락값 확인.
- [ ] 기술 결정 및 미결정 항목 정리.

**인수 기준:** PRD P0와 E2E를 추적할 수 있고 승인된 설계와 미결정 사항이 구분된다. 원본을 수정·공개하지 않는다. 테스트 경계 사용자 확인을 기록하고 실제 문서 PR 링크를 제공한다. 문서 작성 완료와 제품 구현 완료를 구별한다.

## 3. 로그인·프로필·동의

## 4. 일정 신청·이용권·모의 결제

**위치:** 참가 신청·이용권·결제 → 일정 신청·이용권·모의 결제

**선행:** 3.

**산출물:** 참가자가 모집 회차를 보고 복수 날짜·지역과 이용권을 선택해 신청/모의 결제를 완료하고 신청·결제·매칭 대기 상태와 정책을 확인한다.

- [ ] 복수 일정·이용권·결제 흐름 구현.
- [ ] 실패·중복 요청 검증.

**인수 기준:** APP-01~04, PAY-01~02, STA-01~02를 검증한다. 1회권·모의 구독 범위와 U03·U04를 확정한다. 회차·모집 지역을 운영자가 설정할 최소 기능과 권한을 이 흐름에 포함한다. 중복 제출/결제·실패·미결제 제외 조건과 분리된 상태를 확인한다. 실제 PG 결제가 수행됐다고 표시하지 않는다.

## 5. 규칙·데이터·정답 기준

**위치:** 자동 매칭·실패 해결 → 규칙·데이터·정답 기준

**선행:** 1. 입력 정리·규칙·독립 정답 데이터는 배포나 결제 구현 없이 검토할 수 있다. 기본 일정에서는 4 이후 수행한다.

**산출물:** 문서화된 필수조건·점수·목적함수와 정규화된 테스트 입력에 대해 독립 검증자가 같은 정답 기준을 사용할 수 있다. 엔진 구현의 기대값을 복사하지 않는다.

- [ ] 입력 정규화·누락값·식별 정책 결정.
- [ ] 100명 실행 사례와 작은 정답 사례 준비.
- [ ] 매칭 점수·제외 조건 기준 확정.

**인수 기준:** U05~U09·U14·U17·U19의 관련 정책을 명시한다. 원본 응답/고유 사용자/과거 이력을 구분하고 보완 데이터의 생성 근거를 기록한다. 날짜·연령·지역·제외·인원 경계와 유효 4+4 사례를 포함한다. 작은 후보군의 독립 정답 산출 기준과 100명 수용 기준을 확정한다. 준비 Work이므로 별도 UI를 억지로 추가하지 않는다.

## 6. 예약 매칭·재배치·실패 해결

**위치:** 자동 매칭·실패 해결 → 예약 매칭·재배치·실패 해결

**선행:** 4, 5.

**산출물:** 유효한 결제 완료 신청이 마감 시각에 자동 매칭·재배치·확정되고, 미매칭 참가자는 대안 선택으로 이동/보관/환불을 처리하며 상태와 이유를 확인한다.

- [ ] 자동 실행·확정·대안·이동/환불 구현. PRD의 이용권 보관도 같은 해결 흐름에 포함.

**인수 기준:** MAT-01~13, STA-03~06, PAY-03과 재배치 순서를 검증한다. U07·U12·U13 등 필요한 상태/복구 정책을 확정한다. 회차 자동 실행 설정·매칭 이력·예외 조회의 최소 운영자 흐름을 함께 제공한다. 3명 확정·7명 확정·연령 초과·제외 관계·동의 밖 이동·중복 배치를 막는다. 반복/중단 실행에도 중복 테이블/권리 사용/환불이 없고 후보 누락이 없다.

## 9. 운영자 예외·안전 종합 관리

**위치:** 운영자 예외·최종 검증·제출 → 운영자 예외·안전 종합 관리

**선행:** 8. 그 이전의 예외·권한·기본 운영 설정은 각 기능 Work에서 제공한다. 이번 Work는 종합 화면과 전체 연결을 완성한다.

**산출물:** 운영자가 정상 참가를 승인하지 않아도 전체 자동화 현황과 미해결 예외·안전 조치·감사 이력을 한곳에서 확인하고 처리한다.

- [ ] 기능별 예외·조치 연결.
- [ ] 권한·처리 이력 검증.

**인수 기준:** PRD §11·§16의 대시보드, 회차/신청/결제/매칭/식당/채팅/발송/참석/피드백/신고 조회와 필요한 운영 설정·CSV를 종합 검증한다. 권한 없는 열람/조치를 막고 변경 주체·시각·원인·결과를 기록한다. 정상 흐름 수동 승인 관문을 추가하지 않는다.

## 10. 통합 검증·제출

**위치:** 운영자 예외·최종 검증·제출 → 통합 검증·제출

**선행:** 9.

**산출물:** 심사위원이 배포 링크·테스트 계정으로 12단계 E2E와 예외·복구 시나리오를 확인하고 개발자는 검증 근거와 실제 비용/성능 측정을 제출한다.

- [ ] 12단계 E2E·100명·복구 검증.
- [ ] 테스트 계정·배포 링크·증거 제출 준비.

**인수 기준:** 실제 예약 실행·기기 푸시와 모의 경로를 구분한다. 독립 검증 결과·소규모 정답 비교·100명 측정·권한·중복/중단 복구 결과를 기록한다. DB 백업/복원과 결과 안내까지의 가용성·비용 관리, 모바일 원격 작업 경로를 확인한다. Blaybus에는 실제 작업/시간/PR·CI 증거를 기록한다. 미완료 P0를 제출 완료로 숨기지 않는다.

## 검토할 항목

1. 기존 Work 10개를 Issue 10개로 유지하는 크기가 적절한가. 현재는 등록 구조를 보존하며 구현 Task는 좁은 사용자 흐름별 PR로 나눈다.
2. 직접 선행 관계가 실제로 착수를 막는 조건인가. 단순 일정 순서를 가짜 의존성으로 만들지 않았는가.
3. 병합/분할이 필요하면 사용자에게 Blaybus 수정 위치·이유·완료 기준·일정 영향을 먼저 제공한다. 승인 전 Work를 임의 분할하거나 Issue를 추가하지 않는다.

Work 10개의 분할/의존성은 기준안으로 승인되었고 제품 외부 행동 주 경계와 작은 매칭 정답 비교 보조 경계도 사용자 확인을 받았다. 이후 실제 결과를 근거로 변경안을 제시한다.
