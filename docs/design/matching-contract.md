# 예약 매칭 실행 계약 (Work #6 Task ①-a)

## 2026-10-17 PRD 정렬 점수·최소 점수 개선 (ADR-0011)

사용자 조건부 승인. 점수·최소 점수·전체 배정 목적함수·실패 상태의 기준은 [ADR-0011](../adr/0011-prd-matching-score-and-objective.md)이며 아래 본문의 "점수·성비·MBTI 미반영(U05)", "배정 규칙(U06 제안): 인원 최대 → 제출순", "미배치는 `NO_MATCH`" 서술을 **대체**한다. worker·회차 잠금·실행 세대·확정 트랜잭션·1회권 사용 산출은 그대로다.

- 실행 기록에 알고리즘·정책 버전과 정책 값(가중치·최소 점수)을, 테이블에 항목별 점수와 총점을 남긴다. 운영자 이력에는 보이고 참가자 응답에는 넣지 않는다(MAT-12).
- 배정 실패는 `ALTERNATIVE_OFFERED`로 기록한다. 기존 `NO_MATCH` 행은 변환하지 않고 대안 조회는 두 값을 허용한다. 대안 조회는 여전히 읽기 전용이며 이동·보관·환불 선택은 미구현이다.
- 새 실패 이유: `excluded_pair`(제외 관계 때문에 앉을 테이블이 없음), `below_min_score`(최소 점수 이상 테이블을 만들 수 없음).
- `age-ordered-dp-v2`는 초기 배정과 회귀 기준선으로 유지한다. 이미 실행된 운영 결과는 변경하지 않는다.

## 2026-10-17 확정 권리와 대체 일정 조회 보완

기존 승인 범위 안의 구현이다. 1회권 사용 상태는 [결제 계약](./payment-contract.md)의 영구 배치 이력에서 산출한다. 별도 권리 변경 트랜잭션이 없어 확정 실패 롤백과 재실행이 이중 사용을 만들지 않는다.

`GET /api/me/applications/{id}/alternatives`는 참가자 본인의 SUBMITTED·NO_MATCH 신청에만 허용한다. 타인/없는 신청은 같은 404, 다른 상태는 409 `alternatives_not_available`, 익명 401·운영자 403이다. 응답은 no-store이며 공개 회차 정보만 담는다.

- `pending_candidates`: 기존 동의 후보 중 결제 적격이고 SUCCEEDED 실행이 아직 없는 회차. 발표 시각이 지났어도 실행 대기/재시도가 남으면 포함한다. 이 값이 있으면 대체 목록은 비운다.
- `alternatives`: 남은 적격 후보가 없을 때 현재 모집 중인 회차를 시작 시각·지역 순서로 표시한다. 본인의 다른 신청을 포함해 이미 살아 있는 후보인 회차는 제외한다. 현재 목록이며 좌석·식당 확보나 이전 결제의 적용을 보장하지 않는다.
- 조회는 신청·후보·매칭 축·결제·권리를 변경하지 않는다. ALTERNATIVE_OFFERED 전이, 일정 이동/동의, 보관·환불·멤버십 연장은 구현하지 않았다. 따라서 ①-c와 Work #6은 부분 완료다.

검증·미완료는 [진행 기록](./overnight-implementation-2026-10-17.md)을 따른다.

## 실행 트리거와 순서

- 매칭 시각은 회차의 `matches_at`이며 DB CHECK가 `closes_at <= matches_at <= starts_at`을 보장한다. 신청·결제 마감은 `closes_at`이다.
- 실행기는 운영자 수동 시작 없이 주기적으로 실행된다(MAT-01). 별도 실행기 프로세스(`serentable.worker`)의 주기 루프에서 **`matches_at <= DB 시각`이고 아직 성공한 실행 세대가 없는 회차**를 찾아 실행한다. 폴링 주기는 구현에서 정하며 계약 조건이 아니다.
- 한 회차의 실행은 **한 트랜잭션**에서 끝난다. 실행 단위는 회차 하나이며, 회차 사이에는 공유 상태가 없다(신청 소유권 규칙만 공유).
- **U07 제안 — 승인됨(2026-10-17):** 여러 후보 회차가 있는 신청은 **가장 이른 `matches_at` 회차부터** 처리한다. 실행기가 회차들을 매칭 시각 오름차순으로 처리하므로 별도 전역 배치를 만들지 않는다. 같은 시각의 회차 순서는 회차 id로 고정한다(결정적 순서).

## 트랜잭션·잠금·시각

- 실행 시작 시 대상 회차 행을 `SELECT ... FOR UPDATE`로 잠그고, `locked_now(connection)`(DB `clock_timestamp()`)로 시각을 읽는다. 이것이 [신청 계약](./application-contract.md) "마감 판정과 잠금"이 요구한 매칭 실행기의 선행 조건이다.
- 잠금 뒤에 `matches_at <= now`를 다시 확인한다. 잠금을 기다리는 동안 조건이 깨졌으면 실행하지 않는다(잠금 대기 중 다른 실행기가 먼저 끝낸 경우 포함).
- 잠금 순서는 **회차 → (회차에 속한) 신청 → 배치 저장**으로 고정한다. 신청·참가자 행 잠금을 새로 잡지 않는다. 참가자 단위 잠금은 제출·취소 경로 전용이다.
- 실행 중 제출·취소는 회차 행 `FOR SHARE`(제출·취소)와 `FOR UPDATE`(실행)로 경합한다. 실행이 먼저 잠그면 그 뒤의 제출·취소는 `closes_at`이 지났으므로 각각 422 `slot_not_recruiting`·409 `application_cancel_closed`로 거절된다.

## 대상 집합

실행 시점의 대상은 `matching_eligible_applications(connection, slot_id, now)`가 반환하는 제출순 목록이다(SUBMITTED + 그 회차 후보 `live` + `least(now, closes_at)`까지 결제 완료). 여기에 실행기 규칙을 하나 더 적용한다.

- **U07 제안 — 승인됨(2026-10-17):** 이미 다른 회차에서 `CONFIRMED`된 신청은 이 회차의 대상에서 제외한다. 한 신청의 살아 있는 배치 소유권은 최대 하나다(PRD §"같은 신청의 살아 있는 배치 소유권은 하나"). 확정된 신청의 나머지 후보 행은 지우지 않고 이력으로 보존한다.
- 같은 사용자가 시간이 겹치는 서로 다른 신청을 가진 경우(사용자 단위 충돌)는 **U07 미결정**이며 이 계약에서 다루지 않는다. 현재 구현은 신청 단위로만 소유권을 본다.
- 제외 관계(U09)의 출처 테이블은 아직 없다. 실행기는 **빈 제외 집합**을 넘기고, 입력을 어디서 만들지는 ①-c/②에서 정한다.

## 배정 규칙 (U06 제안 — 승인됨, 2026-10-17)

### 하드 조건 (완화 불가, 오라클과 같은 정의)

`tests/oracle/hard_constraints.py`의 `validate_assignment()`가 정의하는 조건을 그대로 쓴다: 테이블 구성원 4~6명, 전원 결제 완료, 테이블 회차에 동의, 출생연도 최대−최소 ≤ 8, 제외 관계 쌍이 같은 테이블에 없음, 한 참가자가 두 번 배치되지 않음. 엔진은 이 모듈을 import하지 않는다(오라클 독립성 유지).

추가로 회차 정원(`event_slot.capacity`)을 넘지 않는다. 4명 미만 테이블은 만들지 않고 7명 이상으로 억지 확정하지 않는다(PRD).

### 목표·우선순위 (U06 — 승인됨, 2026-10-17)

1. **1순위: 확정 인원 최대화.** 하드 조건만으로 동시에 앉힐 수 있는 인원을 최대화한다. 이 값은 오라클 `max_seatable()`의 `seated_count`와 같은 의미이며, 검증에서 두 값을 비교한다.
2. **2순위(동점): 제출순.** 같은 인원을 달성하는 배치가 여럿이면 제출이 이른 신청이 먼저 배정된다.
3. **점수·성비·MBTI는 반영하지 않는다(U05 미결정).** 점수 도입은 U05 확정 뒤 별도 실행 세대로 하고, `match_run`에 규칙 버전을 남겨 이전 결과와 구분한다.

알고리즘은 입력 규모에 따라 구현이 정한다(작은 입력은 결정적 전수·백트래킹). 실행당 100명 수용 기준·제한 시간은 U19이며 이 계약은 정하지 않는다. 알고리즘·규칙 버전 문자열을 `match_run`에 저장한다.

### 배정 불가 처리

- 하드 조건으로 앉힐 수 없는 신청은 `NO_MATCH`로 두고 `reason_code`에 이유(예: `not_enough_eligible`, `age_gap`, `excluded_pair`, `capacity`)를 남긴다.
- **미배치 판정의 두 값 구분은 ①-c에서 정한다.** 이 계약은 `NO_MATCH`까지만 쓰고 `ALTERNATIVE_OFFERED`(대안 제시) 상태는 ①-c(대안·이동/보관/환불)에서 추가한다. 임의 환불·미동의 회차 이동은 하지 않는다.

| `match_participation` | 신청당 현재 매칭 상태 한 행(`application_id` PK), 상태, 확정 회차·배치, 이유 코드, 갱신 시각 | 상태 CHECK(PRD 매칭 축 값), 신청 FK |

- 매칭 상태는 신청·결제 상태와 합치지 않는다. `application.state`는 그대로 `DRAFT/SUBMITTED/CANCELED`이고 매칭 축은 `match_participation.state`다.
- 배치를 **해체·재배치**할 때 살아 있는 `table_assignment`·`dining_table`은 지우지 않고 종료 시각·이유를 남긴다(①-c/재배치에서 완성). ①-b는 확정만 만든다.
- 매칭 이력 조회(운영자)는 `match_run`·`match_run_member`로 설명 가능해야 한다(PRD 이야기 47).

## 상태 전이 (①-b 범위)

| 전이 | 조건 |
|---|---|
| (없음) → `WAITING` | 매칭 대상이 되는 신청(적격). 화면 표시용이며 저장 여부는 구현에서 정한다 |
| `WAITING` → `MATCHING` | 실행기가 회차 실행을 시작(회차 잠금 후). 같은 신청이 동시 실행에 중복 참여하지 않음 |
| `MATCHING` → `CONFIRMED` | 배치에 배정됨. 같은 트랜잭션에서 필수조건·정원·소유권(배치 하나) 재검증 |
| `MATCHING` → `NO_MATCH` | 하드 조건으로 배정 불가(이유 보존) |
| 해당 없음 → `EXCEPTION` | 자동 복구 불가(잠금·저장 실패 등). 원인·대상·시도 보존, 운영자 조회 대상 |

`REALLOCATING`·`ALTERNATIVE_OFFERED`·`TRANSFERRED`는 ①-c, 확정 후 취소·충원(U13)은 후속 Work다.

## 멱등·재시도·중단 복구

- 같은 회차의 실행은 **성공한 세대가 있으면 다시 실행하지 않는다**(자동 재실행 없음). 재실행·강제 재실행은 후속 결정이다.
- 실행 트랜잭션은 전부 롤백되거나 전부 커밋된다. 프로세스 중단으로 `RUNNING` 세대가 남으면 다음 주기에서 그 세대를 `ABANDONED`로 정리하고 새 `attempt`로 다시 실행한다.
- 같은 실행을 두 번 저장하지 않는다: 실행 세대 UNIQUE와 회차 `RUNNING` 부분 UNIQUE가 막고, 배치도 실행 세대별로만 만든다.
- **매칭 실패 횟수만큼 이용권 연장(FAQ Q5)** 은 U03 미확정이므로 구현하지 않는다. `NO_MATCH`를 연장으로 자동 계산하지 않는다. 연장 근거가 필요하면 `match_run_member`의 실패 이유를 쓴다(정책 확정 후).

## API·화면 (최소)

- 참가자: 기존 `GET /api/me/applications` 응답의 매칭 축에 저장된 상태(`CONFIRMED`/`NO_MATCH`/`EXCEPTION`)를 반영한다. 확정이면 회차 요약과 함께 최소 소개(같은 테이블 구성원의 표시명 등, 공개 범위는 U16/`account-profile-contract.md`)를 보여준다.
- 운영자: 읽기 전용 매칭 이력 화면(회차별 실행 세대·결과·이유)을 최소로 추가한다. 수동 확정·수정 API는 만들지 않는다.
- 실행을 촉발하는 공개 API는 만들지 않는다(운영자 수동 시작 없이 자동 실행, MAT-01).

## 검증

- **작은 입력 독립 정답 비교:** 오라클 `max_seatable()`과 실행기 결과의 `seated_count`를 같은 입력(≤12명)에서 비교한다. 배치는 달라도 되고 인원만 비교한다. 실행기 결과는 `validate_assignment()` 위반 0이어야 한다.
- **실제 PostgreSQL 통합 시험:** 마감 전 실행 안 됨, 결제 미완료·취소 신청 제외, 이미 확정된 신청의 다른 회차 제외, 동시 실행 1회만, 중단 후 재시도 시 중복 배치·중복 세대 없음, 4명 미만·7명 확정 없음, 나이차·제외쌍·미동의·정원 위반 0. 기존 `tests/test_failure_and_duplicates.py`의 외부 잠금 보유 방식으로 잠금 대기를 재현한다.
- **브라우저 E2E:** 회차 마감·매칭 뒤 참가자 화면에 확정 상태와 최소 소개가 보이고, 미배치 신청은 이유가 보인다. 모바일 Chromium 에뮬레이션이며 실제 기기 검증이 아니다.
- 통과 결과는 제품 외부 행동(HTTP·화면)과 오라클 비교를 주 경계로 하고, 설계 검토·시뮬레이션을 제품 시험 통과로 표시하지 않는다.
