# UI 개선 목록 (사용자 실기기 확인, 2026-10-20)

심사 제출 이후로 미룬 항목이다. 2026-10-20 사용자가 iPhone·iPad·MacBook에서 운영 배포본(`b633118`)을 직접 열고 확인한 화면을 근거로 기록한다. 스크린샷의 계정·값은 합성 데이터이며 실제 개인정보가 아니다.

**진행 상태(2026-10-20):** 2·3·4·6번을 브랜치 `feat/admin-ui-fixes`에서 구현했고 **아직 병합하지 않았다.** 1번은 홈 화면 웹앱 모드에서 재확인 대기, 5번은 마스킹 정책 확인 대기다. 각 항목의 `구현` 줄에 실제로 바꾼 것을 적는다.

우선순위 판단: 아래 항목은 모두 12단계 인수 흐름을 막지 않는다. 11단계 2회차 실행과 실기기 확인은 **아직 끝나지 않았고**(2026-10-20 밤 기준 미실행) 이 목록의 수정과 별개로 진행한다.

## 1. 하단 내비와 브라우저 툴바 사이 본문 비침

- 화면: 참가자 `/participant`, iPhone Safari 탭
- 증상: 하단 고정 메뉴와 Safari 하단 툴바 사이 좁은 띠로 본문 텍스트(`10월 19일 (월) 22:54 ~ 22:04, 종료`, `정원 4명`)가 그대로 비쳐 읽힌다.
- 사용자 판단: **Safari 탭에서만 생기는 문제이며 홈 화면 웹앱으로 열면 나타나지 않는다.** 웹앱 등록 후 재확인하고, 그때도 남으면 고친다.
- 후보 조치: 하단 내비에 safe-area를 포함한 그라데이션/블러 마스크, 또는 스크롤 컨테이너 하단 여백 추가.
- 완료 기준: 홈 화면 웹앱과 Safari 탭 **양쪽**에서 내비 아래로 본문이 선명하게 읽히지 않는다. 360px에서도 가로 넘침이 없다.

## 2. 최초 접속 안내 카드

- 요구: 처음 접속하면 반투명 배경 위에 카드 형식 안내가 뜨고, **건너뛸 수 있다.**
- 미결정(사용자 확인 필요): 매 접속 표시 여부, 나중에 다시 보는 경로를 더보기 메뉴에 두는 것이 맞는지.
- **결정(잠정, 2026-10-20):** 표시 여부는 `sessionStorage`에 남긴다. `localStorage`는 쓰지 않는다. 이 앱은 "기기에 아무것도 남기지 않는다"를 계약으로 두고 `frontend/e2e/shell.spec.ts`가 `Object.keys(localStorage)`가 비어 있음을 두 곳에서 확인한다. 안내 카드 하나 때문에 그 계약을 느슨하게 만들지 않았다. 대신 브라우저를 닫으면 다시 뜬다. **최초 1회만 기억하는 편이 낫다고 판단되면 `localStorage`로 바꾸고 위 두 단언을 "세션·신원 키는 남지 않는다"로 정밀화하는 별도 결정이 필요하다.**
- 구현: `frontend/src/guide.tsx`(신규)의 `FirstVisitGuide`. 역할별 문구(참가자/운영자)를 나누고, `frontend/src/main.tsx`가 로그인한 사용자에게만 렌더한다. 닫기는 기존 `AppDialog`(반투명 backdrop, Esc, 닫기 버튼)를 재사용했다. 다시 보기는 더보기 대화상자의 `처음 안내 다시 보기` 버튼이 `GUIDE_EVENT`를 보내는 방식이다(`frontend/src/ui.tsx`, `frontend/src/app-navigation.tsx`).
- 완료 기준: 최초 방문에 카드가 뜨고 건너뛰기로 닫힌다. 같은 브라우저 세션에서 새로고침 후 다시 뜨지 않는다. 키보드와 스크린 리더로 닫을 수 있고 터치 목표 44px 이상이다.

## 3. `/admin/safety` 노쇼 후보 구분 불가

- 증상: 노쇼 후보 4건이 모두 표시명 `배포 확인 참가자`와 `10월 19일 (월) 22:54 · 홍대`로 같아 **누가 누구인지 구분할 수 없다.** 각 행에 `노쇼 확정`·`사유 인정(면제)` 버튼만 있고 대상 식별자가 없다.
- 원인 구분: 4명이 같은 표시명을 쓰는 것은 배포 검증 도구의 합성 프로필(`display_name: "배포 확인 참가자"`) 때문이다. 다만 **표시명이 겹칠 때 대상을 구분할 수단이 화면에 없다는 점은 실제 UI 결함**이다.
- **제약(2026-10-20 확인):** `login_id`를 응답에 더하는 방식은 쓸 수 없다. `tests/test_attendance.py:127`이 `no-show-candidates` 응답에 `contact`·`instagram`·`login_id`·`phone`이 들어가지 않도록 단언한다. 실제로 이 방식으로 고쳤다가 그 테스트가 실패해 되돌렸다.
- 후보 조치: 이미 응답에 있는 `user_id` 앞자리를 구분자로 쓰거나, 표시명이 겹칠 때만 회차 식별자를 함께 표시한다.
- 구현: `frontend/src/attendance.tsx`. 같은 표시명이 둘 이상일 때만 그 행들에 `참가자 <user_id 앞 8자>`를 덧붙이고, 결정 결과 안내에도 같은 구분자를 넣는다. 겹치지 않으면 아무것도 덧붙이지 않는다.
- 완료 기준: 표시명이 같은 후보가 둘 이상이어도 조치 대상이 화면에서 유일하게 결정된다. 조치 전 확인 단계에 대상이 다시 표시된다. 위 제약을 깨지 않는다.

## 4. `/admin/venues` PC 넓은 화면 폼 폭

- 증상: 데스크톱에서 입력 필드가 화면 끝까지 늘어나 한 줄에 글자 하나가 들어가는 폭이 된다. 라벨과 입력의 세로 간격도 넓어 밀도가 낮다.
- 추가: 제목 `식당 배정 관리`에 파란 포커스 링이 남아 있다.
- 후보 조치: 운영자 폼에 최대 폭(예: 40rem)과 2열 배치를 주고, 제목 포커스 링을 제거하거나 의도한 위치로 옮긴다.
- 구현: `frontend/src/gatherings.tsx`의 폼에 `operator-form` 클래스를 주고 `frontend/src/style.css`에 `max-width: 34rem`을 뒀다. 좁은 화면의 1열 배치는 그대로다. 파란 링은 `main h1:focus`에서 지웠다(화면 이동 때 스크린리더 안내를 위해 `main.tsx`가 제목으로 focus를 옮기는데, `tabindex="-1"`이라 Tab으로는 닿지 않는다).
- 완료 기준: 960px 이상에서 입력 필드가 읽기 좋은 폭을 넘지 않고, 라벨-입력-버튼이 한 화면에 들어온다. 좁은 화면에서는 기존 1열이 유지된다.

## 5. `/admin` 참가자 관리 목록·상세

- 증상 1: 좌측 목록과 우측 상세가 같은 데이터를 중복 표시한다. 목록 4행이 전부 `배포 확인 참가자`로 같고 `상세 보기` 버튼만 반복된다. 항목 3과 같은 원인이다.
- 증상 2: 우측 상세에 연락처 `010-0000-0000`과 Instagram ID가 원문으로 보인다. 합성 값이라 노출 자체는 문제가 아니지만, **운영자 화면의 마스킹·감사 정책과 맞는지 확인이 필요하다**(`security-verification-plan.md`).
- 후보 조치: 목록에 계정 ID·역할·상태를 함께 표시하고, 상세 접근을 감사 기록과 연결한다.
- 완료 기준: 목록에서 대상을 유일하게 식별할 수 있고, 상세 조회가 감사 기록에 남는다. 마스킹 여부는 정책 확인 후 확정한다.

## 6. `/admin/events` 잘못된 입력 피드백

- 증상 1: 잘못된 값을 넣어도 **팝업이 뜨지 않고** 폼 위 인라인 배너만 나온다. 사용자는 팝업을 기대했다.
- 증상 2: 입력 검증 순서 때문에 **엉뚱한 문구가 먼저 나온다.** `frontend/src/events.tsx:80`이 빈 항목을 먼저 검사해 `모든 항목을 입력해 주세요`를 띄우고, 종료<시작 같은 순서 오류(`:85`)와 마감/매칭/시작 순서 오류(`:89`)는 그 뒤에 있어 도달하지 못한다. 실제로 종료 시각이 시작보다 이른 값과 빈 신청 마감을 함께 넣으면 순서 오류가 아니라 "모든 항목을 입력해 주세요"가 나온다.
- 증상 3: 회차 목록의 각 행에서 `신청 마감`이 값 없이 홀로 표시되어 **깨진 입력 필드처럼 읽힌다.** 실제로는 `slot.recruiting`이 false일 때의 모집 상태 배지다(`frontend/src/events.tsx:200`). 모집 상태임을 드러내는 표기가 필요하다.
- 후보 조치: 제출 시 문제를 **한 번에 모두** 모아 필드별로 표시하고, 요약은 팝업으로 띄운다. 팝업이 열리면 첫 오류 필드로 focus를 옮기고 Esc로 닫을 수 있게 한다. 목록 배지는 `모집 종료`처럼 상태임이 드러나는 문구로 바꾼다.
- 구현: `frontend/src/events.tsx`. `collectProblems()`가 빈 항목과 순서 문제를 한 번에 모은다(빈 항목이 있으면 순서 검사는 하지 않는다 — 값이 없으면 순서를 판단할 수 없다). 문제가 있으면 기존 `AppDialog`를 팝업으로 띄우고, 닫을 때 첫 문제 필드로 focus를 옮긴다. 필드마다 `aria-invalid`와 인라인 문구를 함께 표시한다. 목록 배지는 `신청 마감` → `모집 종료`로 바꿨다.
- 완료 기준: 종료<시작과 빈 신청 마감을 함께 넣으면 두 문제가 모두 필드에 표시된다. 팝업이 뜨고 Esc·닫기 버튼으로 닫히며 입력 내용은 유지된다. 회차 목록에서 상태 문구를 빈 필드로 오해하지 않는다.
