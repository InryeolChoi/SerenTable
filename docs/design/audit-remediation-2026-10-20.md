## 데이터·API·상태 경계

- `0015_matching_explanations`: dining_table·match_run_member에 nullable JSONB explanation 추가. 과거 NULL을 현재 프로필로 소급 계산하지 않는다. 테이블: 출생연도 범위, 성비/MBTI 구성·미기록 수, 공유 관심사 인원, 이전 성공 확정 동석 쌍과 새로운 사람 점수에 반영한 쌍. 개인: 희망 성향별 기존 산식 충족률, 같은 테이블의 이전 확정 동석 인원, 신청에서 동의한 대안 이동 횟수. 실제 참석 확인과 구분한다.
- `0016_venue_condition_review`: venue_allocation에 nullable reviewed_conditions_snapshot 추가. 마지막 적합성 확인 기준이며 원래 배정 원문이 아니다. 과거 NULL은 기준 미기록 재검토로 남긴다.
- `GET /api/admin/match-runs`: 테이블/확정 멤버 explanation 추가. 기존 필드·점수·알고리즘·정책 유지, 참가자 응답에는 넣지 않는다.
- `GET /api/admin/exceptions`: matching_failure 읽기 전용 항목, VENUE_CONDITIONS 읽기 전용 해소 경로 추가. 일반 메모 resolve로 우회하지 못한다. dashboard의 open_exception_count에 미복구 매칭 실패를 포함한다.
- `GET /api/admin/gathering-tables`: 현재 배정 inventory ID·review_required·조건의 허용 식비 추가. 기존 food_snapshot 이름은 유지하되 버전1 통합 조건 digest(음식·알레르기·정렬 식비)로 사용한다.
- 기존 food-approvals POST는 최신 digest·현재 배정 inventory·가격·좌석을 검사한다. 확인 기록·마지막 검토 기준·예외 해소·감사는 한 트랜잭션이다. 동일 확인은 멱등이며 감사 실패 시 모두 롤백한다.
- 신청·결제·매칭 상태 전이는 바꾸지 않는다. 재검토 예외만 OPEN→RESOLVED→재변경 시 OPEN으로 관리한다. worker 사이 A→B→A로 돌아와 현재 조건이 같으면 별도 편집 사건을 만들지 않는다. 종료 모임은 소급 처리하지 않는다.
- 리마인드는 방·앱 내 알림에 동일 정보를 저장한다. 잠금화면 푸시는 기존 일반 안내 문구를 유지하며 개인 조건/상대 평가를 노출하지 않는다.

## 최종 실행 기록

최종 커밋·전체 백엔드·Chromium·WebKit·CI 결과는 검증 완료 후 이 절에 추가한다. 중단한 이전 기준 단일 시험의100 PASS나 DB 이름 안전 가드로 중단된 Chromium22 PASS/2 중단을 최종 전체 통과로 사용하지 않는다. 기존 브라우저 안전 가드를 완화하지 않고 새 전용 컨테이너의 허용 이름 DB로 재실행한다.

## 운영 반영 전 남은 항목

운영 migration·데이터 생성/수정·매칭 재실행·배포·main 병합은 실행하지 않는다. 신규 nullable migration도 별도 승인 후 적용해야 한다. legacy 배정은 재검토 예외가 생길 수 있으므로 운영자가 현재 조건을 확인할 준비가 필요하다.

U13 확정 후 취소·충원·재배치, 운영자 역할 분리/조치 사유 전반 등 미정 정책은 이번 수정으로 승인하거나 완료 처리하지 않는다. 배포 환경11단계 두 번째 회차·후기 리마인드, Android 실기기·장시간/극한 부하·운영 DB/백업 최신성은 별도 인수다. 기존 제한적 부하·로컬 기능 회귀를 전체 스트레스 완료로 표현하지 않는다. iPhone 잠금화면 수신은 기존 사용자 확인 근거이며 이번 재시험이 아니다.

### A7 전체 실행에서 추가로 드러난 시각 전제

코드 `2ea76c2`의 새 빈 DB 단일 전체 실행은 377 PASS/1 FAIL/4 ERROR(931.12초)였다. push 예외 시험은 발송3건 단언에2건만 처리됐고, 추천 fixture 네 개는 `run_due_matches()`가 빈 목록이었다. 같은 파일 묶음은 별도 실행8 PASS여서 이 결과를 전체 통과로 합산하지 않았다.

호스트의 시험 입력 시각을 DB보다1초 앞서게 한 격리 probe에서 **동일한 발송2/3 실패와 빈 매칭 결과**를 각각 재현했다. 제품 엔진·DB 시계는 바꾸지 않았다. 시험 회차 마감은 DB 시각에서 만들고, 짧은 기한 대기는 실제 DB의 matches_at 도달을 확인하며, 직접 만든 발송 fixture의 시각도 DB에서 읽도록 수정했다. 발송3건·매칭4명·권한/이력의 기존 단언은 유지한다. 호스트가 앞선 추천 시나리오를 영속 회귀에 추가했다. 중앙 fixture에서는 테이블 없는 발송 예외도 명시적으로 정리한다.

시각 차이 probe는 기존 실패와 같은 유형을 입증했지만 **원래 실패 순간의 시각 차이는 측정하지 못했다**. 따라서 원래 네 오류의 원인을 단정하지 않는다. 최종 변경으로 다시 전체 단일 실행·CI를 확인한다.
