# 앱 형태의 UI 보완

## 위치·범위

운영자 예외·최종 검증·제출 → 통합 검증·제출(#10) → 앱형 UI·반응형 개선 및 회귀 검증에 기록한다. 사용자가 Blaybus에 추가하려는 Task의 위치를 확인했으며, 기존 공통 UI·핵심 화면 흐름 설계(#18)는 설계 참고로 연결한다. 사용자 요청은 게시판처럼 나열된 화면을 자연스럽고 반응이 빠른 앱 형태로 구현하는 것이다. 새 Agenda/Work는 만들지 않는다. 기본 브랜치는 PR50이 병합된 main2bd003c이다.

기존 UI 흐름·브랜드 검토·계정/권한·신청/이용권/실패 해결 계약을 유지한다. API·DB·worker·매칭·결제/환불 정책은 변경하지 않는다. 운영 배포·운영 DB 작업은 하지 않는다. Claude의 운영 인수·PWA 메타·푸시 구독 복원 작업과 원본 자료는 수정하지 않는다.

## 디자인 계획과 검토

- 색: 바탕 `#FFF9ED`, 본문 `#422817`, 주색 `#8B4E27`, 보조 `#6A5847`, 경계 `#D7C6AF`, 선택 바탕 `#F4EADB`. 기존 제공 자료 기반 재현 토큰을 유지한다.
- 글꼴: 로고와 화면 주제목은 기존 명조, 본문·입력·조작은 한국어 시스템 sans. 본문16px, 보조13~14px, 모바일 제목28px, 넓은 화면34px를 사용한다. 외부 글꼴·아이콘 라이브러리는 추가하지 않는다.
- 배치: 화면 제목과 현재 작업을 먼저 보여준다. 모바일의 주요 이동4개+더보기는 하단, 넓은 화면은 상단이다. 참가자 본문은740px 읽기 폭, 운영자 목록/상세는960px부터2열이다.
- 원칙: 로고·명조 제목에 식탁 초대장의 성격을 남기고, 나머지는 사용자의 상태와 다음 행동에 집중한다. 큰 홍보 영역·장식용 사진·동일한 카드 반복·자동 등장 효과를 추가하지 않는다.

```text
로고                             알림 / 로그아웃
화면 제목
현재 상태와 다음 행동
해당 화면의 내용
주요 이동: 내 식탁 / 모집 회차 / 모임 안내 / 단체방 / 더보기
```

초기 검토에서 모든 참가자 화면에 선행하는 큰 알림 영역과 같은 위계의8개 메뉴가 실제 작업을 밀어내는 문제를 확인했다. 브랜드 색을 바꾸는 대신 이 정보 위계를 수정했다. 프로필은 기본 정보·성향과 관심사·식사 조건으로 구획한다. 긴 안내는 홈에서 펼쳐 볼 수 있게 하되, 모의 결제 전 환불·취소·노쇼 고지는 기존대로 노출한다.

## 구현

- `app-navigation.tsx`: 역할별 주요 이동·더보기, 현재 화면 표시,44px 이상의 터치 영역, native dialog와 닫기/포커스 복귀. 수정키를 이용한 새 탭 열기는 보존한다.
- `notification-center.tsx`: 상단 알림 버튼으로 즉시 여는 패널. 최초 열기 전에는 알림 컴포넌트를 마운트하지 않아 조회를 시작하지 않으며, 한 번 연 이후에는 닫아도 컴포넌트를 유지해 같은 로그인에서 기기 안내·구독 식별 상태를 잃지 않는다. 사용자 변경/로그아웃 때는 key와 역할 분기로 파기한다. 기존 NotificationsPanel의 통신/푸시 코드를 재작성하지 않는다.
- 프로필: API를 기다리는 동안에도 화면 제목과 대기 상태를 먼저 표시한다. 입력 값은 실제 응답으로 채우고 미저장 값은 기존 부모 draft에 유지한다. 구획·선택 영역·저장 조작을 정리한다.
- 신청/이용권: 참가자에게 내부 WAITING/CONFIRMED 등의 코드 대신 한국어 상태를 보여준다. API 원본 값·판정·결제/매칭/신청의 서로 다른 축은 유지한다. 홈의 상세 안내는 펼침 영역으로 제공한다.
- 운영 콘솔: 별도 JS chunk로 분리해 참가자의 초기 화면에서 운영 도구를 내려받지 않는다. 준비 상태·로드 완료 후 제목 포커스·다운로드 실패 시 복구 안내를 제공하고 다른 메뉴 이동을 유지한다.
- CSS: 화면 크기에 따른 상단/하단 탐색, 안전 영역, 작은 태블릿의1열 운영 화면, 키보드 포커스·reduced motion을 반영한다. 동작에 반응하는 짧은 패널 효과만 사용한다.
- 경제적 상태는 낙관적으로 완료하지 않는다. 결제·환불·매칭 성공은 기존 서버 응답을 따른다. 개인정보를 localStorage/전역 캐시에 저장하지 않는다.

## TDD·회귀 기록

기존에 합의한 브라우저 외부 동작과 실제 PostgreSQL/API/별도 worker를 사용한다.

1. 현재 메뉴 표시0·44px 미달을 RED로 확인 → 현재 위치와 터치 영역 보완 후 GREEN.
2. 알림 버튼/패널이 없음을 RED로 확인 → 패널 열기·닫기. 추가로 실제 포커스 복귀 실패를 고쳐 GREEN.
3. profile API를 지연시켰을 때 제목도 사라지는 RED → 제목/대기 안내를 먼저 보여 GREEN.344→744→390 크기 변경 후 미저장 입력 유지.
4. 실제 신청·모의 결제 후 WAITING 내부 코드 노출 RED → 한국어 표시. API 상태 값은 유지하고 기존 매칭/결제 흐름을 재검증.
5. 콘솔 JS를 지연시켰을 때 실제 화면의 포커스 소실 RED → 로드 완료 후 포커스 보완.
6. 알림 닫기/재열기 시 기기 안내 상태 소실 RED → 같은 로그인 동안 컴포넌트 상태 보존.
7. 콘솔 JS 요청을 실패시키면 앱이 사라지는 RED → 에러 경계·새로고침 안내·다른 메뉴 이동 제공.

기존 15개 브라우저 시험 중 홈 정책 안내가 접힌 상태를 직접 확인하던1건은 사용자에게 안내를 펼치는 상호작용을 추가했다. 결제 단계의 고지를 숨기거나 검사 항목을 삭제한 것이 아니다.

중간 Chromium 실행 중 WebKit 준비를 겹쳐 실행해 공용 trace 출력이 삭제되는 ENOENT가1건 발생했다. 제품 실패와 구분한다. 이후 엔진별 출력 경로와 독립 실행/DB로 분리하고 최종 결과를 다시 확인한다. 임시 WebKit 첫 시도는 포트8000 사용 중으로 거절됐으며 기존 서버를 재사용하지 않았다.

최종 통과 수·환경·커밋·CI는 후속 기록과 해당 PR의 Checks를 기준으로 한다. 이미지 및 측정은 `/private/tmp/serentable-app-ui-artifacts/`에 있으며 원본 설문/실제 사용자 데이터는 사용하지 않았다.

## 측정·한계

같은 로컬 Chromium의390px 화면에서 홈 제목 위치가 기존약613px에서약130px로 올라왔다. 화면 크기만 변경해도 입력 값은 유지된다. 로컬 알림 열기5회의두 animation frame 시점은 약11~32ms였다. 이는 UI 열림 관찰이며 서버 처리·네트워크·실제 기기 성능 보장이 아니다. 패널 효과는140ms, reduced motion에서는 생략한다.

실제 iPad/폴더블의 힌지·가상 키보드·PWA 수신/구독 재진입 인수는 별도로 남긴다. ‘아이폰듀오’ 모델을 특정하거나 출시/지원 사실을 가정하지 않는다.

## 검토용 PR 생성 전 확인

- 정식 설정으로 로컬 Chromium 21개·WebKit 21개 통과. 각 엔진의 `.last-run.json`은 passed/실패 목록 없음이다. 실제 로컬 PostgreSQL 17과 API를 사용했으며 엔진은 순차 실행했다.
- TypeScript 검사·Vite 빌드와 `git diff --check` 통과. GitHub CI는 PR 생성 후 별도로 확인한다.
- Chromium 13개 화면 크기 × 7개 화면의 91회 렌더링에서 넘침을 확인하지 않았다. 최종 WebKit 동일 렌더링 감사와 실제 기기 인수는 별도이며 브라우저 E2E 통과와 구분한다.
- PR은 검토용 Draft로 제출한다. 운영 반영·main 병합은 수행하지 않는다.
