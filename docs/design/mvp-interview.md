## 1라운드 — 기술 선택의 전제와 배포 목표

질문은 아래 세 개이며 서로의 답에 의존하지 않는다. 기술 스택은 아직 결정하지 않는다. 다음 라운드는 답변에 맞춘 스택·배포 구조와 매칭 정책의 주요 모호함이다.

### Q1. 직접 검토하고 고칠 수 있는 기술은 무엇인가?

시나리오: 10/19 밤에 원격 Codex가 만든 변경이 CI에서 실패했다. 본인이 원인을 이해하고 수정 방향을 판단해야 한다.

왜 지금: 익숙한 언어와 새로 배울 수 있는 범위가 스택·테스트·매칭 구현 언어 선택에 영향을 준다. AI의 코드 생성 속도만으로 선택하지 않는다.

- A. TypeScript/React 중심으로 통일: 프론트와 서버의 언어를 맞추기 쉬우나, 해당 생태계가 낯설면 학습 부담이 있다.
- B. 익숙한 Python 또는 Java/Kotlin 등의 백엔드 + 웹 프론트: 서버 판단은 쉬울 수 있으나 두 실행 환경·API 연결·배포를 관리한다.
- C. 특정 스택 경험이 거의 없음: 관리형 서비스와 작은 앱으로 시작하기 좋지만 구현 검증을 위한 학습 시간이 필요하다.

**AI 추천**: 가장 익숙한 기술을 기준으로 선택한다. 경험 차이가 작다면 TypeScript 중심의 단일 앱을 먼저 검토한다. 사용자에게 언어/프레임워크, 배포 경험, 새 기술을 배우는 데 쓸 수 있는 시간을 함께 요청한다.

사용자 답변(최신): “typescript 단일로 갈지, typescript + python으로 갈지 고민해보자. 시간이 많지 않긴 해. 당연히 파이썬으로 가도 Fastapi로 갈 거 같고...”

결정/설계 영향: TypeScript 단일과 TypeScript + Python을 비교한다. Python 채택은 미결정이며 채택 시 FastAPI가 사용자 선호 후보다. 기존 숙련도를 추정하지 않는다. 현재 승인된 언어 구성은 없고 기존 ADR-0001은 비활성 상태로 유지한다.

### Q2. 제출 MVP를 심사용 운영 환경으로 할 것인가, 실제 유료 참가자까지 받을 것인가?

시나리오: 심사위원이 배포 링크에서 신청하고 매칭·채팅·실패 해결·다음 매칭을 직접 확인한다.

왜 지금: 외부 결제·로그인·실제 식당 예약 연동의 범위와 검증 대상을 먼저 정해야 P0 구현 시간을 확보한다. PRD가 허용한 모의 기능을 사용할지에 대한 목표 결정이며, 허용 여부 자체를 재질문하지 않는다.

- A. 심사용 배포 MVP: PRD에서 허용한 테스트 계정·모의 결제/환불을 사용하고 DB 저장·스케줄러·채팅·푸시 등 P0는 실제 작동시킨다. 완주 검증에 집중할 수 있으나 실결제 운영을 증명하지는 않는다. 식당은 사전 등록한 파트너 재고를 자동 배정하며 외부 예약 연동 여부와 구분한다.
- B. 제출 시점부터 실제 유료 참가자 운영: 실제 서비스 연동 경험이 생기지만 외부 승인·실결제 예외 검증·운영 준비가 일정 위험을 키운다.

**AI 추천**: A. 10/20까지 실제 배포한 P0와 12단계 검증을 완성하고 실결제 연동은 후속 범위로 둔다. 푸시를 앱 내 알림으로 대체하거나 채팅을 화면 목업으로 축소한다는 의미가 아니다.

사용자 답변: “심사용 배포 mvp라고 보면 되는데...음 외부 연동도 있긴 해야 하지 않을까”

결정/설계 영향: 심사용 배포 MVP 목표는 확정. 외부 연동의 종류·개수는 미정. 실결제·소셜 로그인 추가가 승인되었다고 해석하지 않는다. Q5에서 가장 작은 범위 확인을 진행한다.

### Q3. 심사 기간까지 유지할 인프라 비용의 상한은 얼마인가?

시나리오: 10/21 제출 뒤에도 심사위원이 접속할 수 있어야 한다. 무료 플랜의 절전·실행 주기·사용량 한도가 핵심 자동화에 영향을 줄 수 있다.

왜 지금: 데이터베이스·백그라운드 작업·알림 서비스의 배치 방식을 결정하기 전에 예산 제약을 정해야 한다. 아래 금액은 예산 선택지이며 실제 서비스 요금 견적이 아니다.

- A. 0원: 비용 부담이 없지만 무료 한도에 맞춰 구성해야 하며 유지 조건을 점검해야 한다.
- B. 월 3~5만원 이내: 필요한 부분만 유료 옵션을 검토할 수 있으나 그 예산으로 모든 서비스를 유료화할 수 있다고 보장하지 않는다.
- C. 월 10만원 이내: 구성 선택의 여지가 넓어지지만 해커톤 규모에 비해 비용이 커질 수 있다.

**AI 추천**: B를 비용 상한으로 두고 무료부터 시작한다. 무료 플랜의 공식 제한과 실제 요금을 확인한 뒤 꼭 필요한 지출만 결정한다. 금액은 사용자가 다른 상한을 정해도 된다.

사용자 답변: “B를 상한으로 두고 하자. 이거 떨어질 가능성도 크자나. 물론 3등을 목표로 하긴 할건데...!”

결정/설계 영향: 월 3~5만원 상한, 무료부터 시작한다. 입상 여부와 무관하게 비용을 제한한다. 서비스별 요금과 과금 구조를 확인하고 불필요한 유료화를 피한다. 공급자·유료 플랜·서비스 생성은 아직 선택되지 않았다.

## 공식 기술 문서 확인 — 선택 전 참고

읽기 전용 조사 에이전트가 공식 문서로 확인했다. 아래는 사실 참고이며 사용자 승인된 스택이 아니다.

- [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers): 한 앱에 화면과 서버 API를 둘 수 있다. 이 구조가 배포 부담을 줄인다는 것은 설계상의 추론이다.
- [Supabase 요금표](https://supabase.com/pricing): Free DB 500MB, 활성 프로젝트 2개, Realtime 동시 연결 200개, 1주 비활성 시 정지, 자동 백업 미포함, API/DB 로그 1일 보관. Pro $25/월부터. 실제 결정 시 요금 및 필요한 추가 비용 재확인.
- [Supabase Realtime](https://supabase.com/docs/guides/realtime): 실시간 기능을 제공하지만 메시지 영속 저장과 참가자별 권한은 설계해야 한다.
- [Supabase Cron](https://supabase.com/docs/guides/cron): 초 단위 예약, SQL/함수/HTTP 실행 가능. 권장 동시 작업 8개 이하, 작업당 10분 이하.
- [Vercel Cron 제한](https://vercel.com/docs/cron-jobs/usage-and-pricing): Hobby는 작업당 하루 한 번, 지정 시각의 시간 범위 안에 실행되므로 분 단위 데모 자동화의 실행기로 선택할 수 없다.
- [Supabase 이메일 인증](https://supabase.com/docs/guides/auth/passwords): 기본 이메일 발송 제한이 있어 심사 계정 제공 방식에 고려해야 한다.
- [Supabase Edge Functions 제한](https://supabase.com/docs/guides/functions/limits): 요청당 CPU 시간 2초 제한. 매칭 연산을 배치하기 전에 대상 규모별 측정 필요.

## 2라운드 — 언어 구성과 추가 외부 연동 범위

### Q4. TypeScript 단일 구성과 Python 병행 중 어떤 구성을 선택할까?

시나리오: 마감 시각에 후보를 매칭하고 확정·식당·채팅·알림으로 연결한다. 10/19 밤에 배포된 매칭 작업 실패를 원격으로 진단해야 한다.

왜 지금: 실행 환경 수와 상태 변경 책임이 CI/CD, 통합 테스트와 매칭 구현 범위를 결정한다. Python 사용 여부는 아직 미결정이다.

- A. TypeScript 단일: Next.js 후보로 화면·어드민·일반 서버·매칭을 같은 언어로 둔다. 연결과 배포 검증 부담이 작다. 매칭은 필수조건 검사와 점수 평가, 제한 시간 탐색·개선 로직을 구현해야 하며 최적해를 보장한다고 주장하지 않는다. 단일 언어가 하나의 프로세스 또는 하나의 배포만을 강제하지는 않는다.
- B. TypeScript + FastAPI 매칭 엔진: 일반 업무는 TypeScript가 담당하고 Python은 후보·제약·이력을 받아 테이블 조합을 계산한다. OR-Tools 같은 최적화 도구를 사용하기 쉽다. 두 실행 환경, API 계약, 타임아웃·재시도·배포 점검이 추가된다. FastAPI는 API 프레임워크이며 매칭 알고리즘이나 영속 작업 실행기 자체가 아니다. 저장·확정 전 최종 검증은 업무 처리 쪽이 책임진다.
- C. TypeScript 화면 + FastAPI 전체 백엔드: 서버 업무와 매칭 책임이 Python에 모인다. 전체 API와 인증·채팅 연결을 구축하고 검증해야 하므로 이번 일정에는 범위가 크다.

**AI 추천**: A를 기본안으로 제안한다. 10/20 완성 목표에서는 실행 환경과 연결 지점을 줄이는 편이 유리하다는 설계 판단이다. 다만 전문 최적화 솔버 활용을 핵심 결과물로 삼고 싶다면 B가 실제 대안이다. B의 라이브러리 사용만으로 모델 정확성이나 제한 시간 내 최적해가 보장되지는 않는다. 어떤 언어든 7명을 억지로 확정하지 않고, 8명에서는 가능한 4+4 조합을 놓치지 않는 등의 검증이 필요하다.

사실 근거: [OR-Tools CP-SAT](https://developers.google.com/optimization/cp/cp_solver)는 Python을 지원하고 최적해·실행 가능 해·불가능·결과 미확정 상태를 구분한다. [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)는 같은 앱에 서버 API를 둘 수 있다. 언어 선택과 최적화 목표/규모는 구별하며 후자는 별도 질문에서 결정한다.

사용자 답변: pending

결정/설계 영향: pending. 언어 구성·프레임워크·매칭 라이브러리 미정. 결정 후 중요한 책임 경계를 ADR로 기록한다.

### Q5. 외부 연동은 어디까지 추가할까?

시나리오: 심사위원이 테스트 계정으로 전체 E2E를 검증하면서 실제 서비스 연결도 확인한다.

왜 지금: 사용자의 “외부 연동도 있긴 해야 하지 않을까”가 무엇을 뜻하는지 확정해야 승인되지 않은 P1 기능으로 범위를 확대하지 않는다. DB·실시간 전송·웹 푸시도 실제 외부 서비스 통신이며, 외부 연동 개수 자체는 심사 배점 항목이 아니다.

- A. 필수 동작용 연결에 집중: 관리형 DB/인증·채팅 전송과 실제 웹 푸시를 구현하고, 테스트 계정·모의 결제/환불 사용. P0 완주에 집중하지만 소셜 로그인이나 PG 결제 연동을 보여주지는 못한다.
- B. A + 실제 Google 소셜 로그인 하나: 외부 계정 로그인 경험을 보여준다. OAuth 설정과 배포/테스트 환경 콜백 검증이 추가된다. 테스트 계정은 심사용으로 유지한다.
- C. A + PG 테스트 결제/취소 연동: 결제 응답·실패·취소 연동을 보여준다. 결제 상태 검증과 외부 테스트 API 처리에 시간이 추가된다. 테스트 연동은 실결제 운영 승인이 아니다.

**AI 추천**: A. 관리형 DB/인증·실시간 채팅과 실제 웹 푸시만으로 외부 연결 경험을 확보하고 자동화 완주에 집중한다. 사용자에게 익숙한 OAuth 설정이 있다면 B를 고려한다. B 또는 C는 추가 선택으로 남기며 승인된 것으로 해석하지 않는다. 외부 연동 개수 자체가 입상 가능성을 높인다고 주장하지 않는다.

사실 근거: [Supabase Google 로그인](https://supabase.com/docs/guides/auth/social-login/auth-google), [Next.js PWA/Web Push 가이드](https://nextjs.org/docs/app/guides/progressive-web-apps). 웹 푸시는 알림 허용이 필요하고 iOS 16.4 이상에서는 홈 화면에 설치된 웹앱에서 지원한다. PWA는 브라우저 기반 웹앱에 홈 화면 설치·알림 기능을 더하는 방식이다. 앱 내 알림은 푸시 미허용/미지원 환경에서도 제공하지만, 이것을 푸시 구현의 대체로 간주하지 않는다. 실제 지원 기기에서 푸시 발송·수신을 별도로 검증한다.

사용자 답변: pending

결정/설계 영향: pending. 추가 외부 연동 대상, 시간 상한과 실패 시 범위 결정 방식이 미정. 다음 라운드는 매칭 규모·정확성 목표 및 PRD 모호함을 우선 다룬다.

### Q6. 식당 연동과 실패 처리를 어디까지 구현할까?

시나리오: 조건에 맞는 테이블이 확정됐지만 해당 지역·시간에 배정 가능한 식당 재고가 없다.

왜 지금: 외부 식당 예약 실패 생략 허용을 내부 재고 부족 처리 삭제로 확대하면 P0 충족 여부가 달라진다. 확인 없이 범위를 바꾸지 않는다.

- A. 가상 식당 재고 자동 배정 + 재고 부족 예외 유지. 외부 예약 API는 제외한다. PRD의 자동 배정·예외 흐름을 보여주면서 외부 연결 부담을 줄인다. 실제 예약 성공은 증명하지 못한다.
- B. 식당은 항상 배정 가능하다고 가정하고 모든 실패 처리를 생략한다. 구현량은 작지만 PRD 식당 부족 예외 요구를 충족하지 못할 수 있어 별도 범위 예외 확인이 필요하다.
- C. 실제 예약 서비스까지 연동한다. 실제 예약을 보여주지만 API 접근·승인·실패 처리와 검증 범위가 늘어난다. 접근 가능한 공식 API가 있다고 가정하지 않는다.

**AI 추천**: A. 외부 예약 실패와 내부 재고 부족을 구분해 Q&A의 단순화 허용을 활용하되 P0 예외 동작은 보존한다. 예약 레코드는 가상임을 구분하고 배정은 실제 저장한다. 아직 사용자 승인된 결정은 아니다.

사용자 답변: “그렇게 하자” — 직전 추천 A에 동의.

결정/설계 영향: A 확정. 가상 식당 재고 자동 배정 및 재고 부족 예외 유지, 외부 식당 예약 API 제외. ADR-0002에 기록.

## 진로 목표 반영 라운드

사용자 Q4 답변: “고민이 되는게, 나는 백엔드를 지망하는 사람(한국은 대부분 자바 백엔드가 많고, 요새 ai 때문에 파이썬 백엔드가 늘어나고 있다만은...)이고, 이 해커톤으로 상 못 타더라도 남는 경험이 분명히 있어야 하는데 ... 음 어떻게 하지”

해석: 백엔드 진로와 입상 여부에 무관한 설명 가능한 엔지니어링 경험을 기술 선택의 중요한 기준으로 삼는다. TypeScript/Python 어느 구성도 아직 선택하지 않았다. 사용자의 채용 시장 언급은 검증된 시장 통계로 취급하지 않는다.

**AI의 수정된 추천 방향**: 완성 속도만 보았던 TypeScript 단일 추천에서, 백엔드 경험 목표를 함께 고려해 TypeScript 화면 + FastAPI 핵심 업무 서버를 우선 검토한다. 단, Python/HTTP/SQL/배포 숙련도를 확인하기 전 선택을 확정하지 않는다. Python 매칭 전용은 전문 솔버 경험에는 적합하나 신청·확정·환불 트랜잭션을 Python에서 경험하는 구성은 아니다. TypeScript로도 같은 백엔드 문제와 검증을 다룰 수 있다. 어느 프레임워크를 사용했다는 사실만으로 채용 경쟁력이나 학습 성과를 보장하지 않는다.

핵심 업무 서버 제안은 한 Python 앱 안에 신청·이용권/모의결제·매칭·확정·예외 책임을 모으는 형태다. 인증, DB 운영, 실시간 전송은 관리형 서비스를 활용하는 후보이며 직접 구현을 늘리기 위한 제안이 아니다. 실행기·스케줄러·공급자·배포 수는 아직 결정하지 않았다. TypeScript 서버와 Python 서버 양쪽에서 같은 업무 상태를 수정하는 구조는 피한다는 추천이다.

### Q7. Python과 백엔드 코드를 어디까지 직접 검토할 수 있는가?

시나리오: Codex가 만든 확정 API에서 동시에 두 요청이 들어와 참가자가 중복 배치되는 오류가 난다. 본인이 코드와 DB 동작을 이해하고 수정 결과를 검증해야 한다.

왜 지금: FastAPI 업무 서버 선택이 경험 확보인지 학습 부담 증가인지 판단하려면 기존 역량을 확인해야 한다.

- A. Python API/SQL/테스트/배포를 해본 경험이 있다. Python 서버 구성을 검토하기 유리하지만 여전히 프론트 연결과 배포 부담은 남는다.
- B. Java/Spring 등 다른 백엔드 경험이 있고 Python 문법은 익숙하다. HTTP·트랜잭션 지식은 활용 가능하나 Python ORM·테스트·배포 도구 학습이 필요하다.
- C. Python이나 서버/SQL/배포가 대부분 처음이다. 학습 기회는 크지만 제한 일정의 위험도 크다.

**AI 추천**: 가장 가까운 수준을 그대로 알려준다. A/B이면 FastAPI 핵심 서버를 더 적극적으로 검토하고, C이면 TypeScript 단일에서 핵심 백엔드 문제를 검증하는 구성을 우선 검토한다. 이는 조건부 추천이고 경험을 추정하지 않는다. 선택지보다 구체적인 기존 프로젝트 경험을 답해도 된다.

사용자 답변: “Java/Spring 등 서버 경험 + Python 문법 익숙함 + 42서울에서 트랜센더스 할 때 Django 해본 적 있음. 인증 구축 등을 해본 적도 있어”

결정/설계 영향: 기존 서버·Python·Django·인증 경험 확인. FastAPI 핵심 업무 서버를 검토할 근거가 생겼지만 Q4 기술 선택은 여전히 pending.

### Q8. 이력서에서 가장 강하게 증명하고 싶은 경험은 무엇인가?

시나리오: 수상하지 않아도 프로젝트 설명에서 자신의 설계 결정과 검증 결과를 제시한다.

왜 지금: 핵심 E2E는 모두 구현하되, 추가 실험·측정·학습 시간을 어디에 쓸지 정해야 한다. 이것은 P0 기능을 생략하는 선택이 아니다.

- A. 운영 자동화의 신뢰성: 중복 실행, 동시 신청/배치, 트랜잭션, 알림 실패 재시도와 복구를 재현하고 검증한다. 백엔드 업무 설계 경험을 설명하기 좋지만 장애 시나리오 구축과 검증에 시간이 든다.
- B. 매칭 알고리즘의 품질: 제약 위반 0, 작은 데이터 최적해와 비교, 인원 증가에 따른 성공률·점수·실행 시간을 측정한다. 최적화 경험을 설명하기 좋지만 점수 모델 및 독립 비교 기준 설계가 필요하다.
- C. 둘을 동일 깊이로 강조: 폭넓은 결과를 보여주나 7일 일정에서 모두 얕아지거나 완성 시간을 침범할 수 있다.

**AI 추천**: A를 주력, B는 필수조건 검사와 작은 데이터 비교를 기본 검증으로 포함한다. B를 선택해도 멱등성·권한·재시도 같은 P0 안전장치는 유지한다. Q7 역량 답과 무관하게 경험 목표를 선택할 수 있다.

사용자 답변: “A를 주력으로, B는 필수조건 검사와 작은 데이터의 정답 비교까지 확보. 백엔드 지원자로서 ‘어떤 오류가 가능했고, 어떻게 막았으며, 무엇으로 검증했는지’ 설명할 결과를 남기자.”

결정/설계 영향: 운영 자동화 신뢰성을 주력으로 확정. 매칭은 필수조건 검사 및 작은 데이터 정답 비교를 확보한다. 구현량이 아니라 재현 가능한 오류·방지 설계·검증 결과를 경험 증거로 남긴다.

사실 참고: [FastAPI 자동 API 문서](https://fastapi.tiangolo.com/tutorial/first-steps/)는 OpenAPI 및 대화형 문서를 제공한다. [배포 개념](https://fastapi.tiangolo.com/deployment/concepts/)은 실행·재시작·프로세스·메모리 등의 운영 책임을 설명한다. API 문서 생성이 트랜잭션 정확성이나 신뢰성 검증을 대신하지 않는다.

## 인프라 라운드 — 배포 공급자와 작업 실행 형태

사용자가 “인프라는 왜 말을 안해ㅋㅋ”라고 요청하여 미뤘던 공급자 선택을 진행한다. 아래는 추천안이며 아직 공급자 선택·유료 서비스 생성 승인이 아니다. 문서만 기록하고 구현은 10/16부터 진행한다.

### 추천 구성의 책임

- Vercel: TypeScript 참가자·어드민 화면. 프론트 프레임워크 선택은 아직 미정이다.
- Railway Hobby: FastAPI API와 같은 Python 코드베이스를 쓰는 작업 실행기. 상시 실행 모드로 구성하는 안이다.
- Supabase Free: PostgreSQL·Auth·Realtime. 인증 토큰 검증과 업무 권한은 FastAPI가 담당한다. 신청·배치·환불 등 핵심 업무 쓰기는 Python에 모으고, Realtime 구독은 테이블 구성원만 허용한다. DB가 무료라는 이유로 백엔드 업무 책임을 브라우저로 옮기지 않는다.
- 웹 푸시: 실행기가 실제 Web Push 발송 및 결과/재시도를 처리하는 후보. Supabase Realtime을 푸시로 오해하지 않는다. 구체 라이브러리·기기 검증은 후속 결정이다.
- GitHub Actions: 테스트 통과한 변경을 배포하는 흐름을 준비한다. 공급자의 단순 push 자동 배포가 CI 완료를 기다린다고 가정하지 않는다. CI 성공과 배포를 연결하는 방법을 별도 설계한다.

### 공식 사실 확인

- [Railway 요금](https://docs.railway.com/pricing/plans): Hobby 최소 월 $5, $5 사용량 포함, 초과 CPU·메모리·저장·송신 사용량 과금. $5 고정 총액이 아니다. [가격표](https://railway.com/pricing)의 메모리 단가는 GB당 초당 $0.00000386, CPU는 vCPU당 초당 $0.00000772다. 작업 실행기 추가는 비용에 영향을 준다.
- [Railway 비용 제어](https://docs.railway.com/pricing/cost-control): hard limit 도달 시 모든 workload가 내려가므로 비용 상한 설정만으로 심사 가용성까지 보장하지 않는다. 실제 메모리·CPU를 배포 후 측정하고 조기 알림/한도를 설계한다.
- [Railway Cron](https://docs.railway.com/cron-jobs): 조사 에이전트 확인상 최소 5분 간격, UTC, 이전 실행이 끝나지 않으면 다음 실행 생략. 짧은 데모 및 정시 자동화에는 제약이 있다.
- [Supabase Free](https://supabase.com/pricing): DB 500MB, Auth·Realtime 포함, 자동 백업 미포함. Pro 월 $25부터라 Railway와 함께 유료화하면 원화 예산에 부담이 생길 수 있다. 실제 원화 총액은 환율·세금·사용량 확인 전 확정하지 않는다.
- [Supabase 비활성 정지](https://supabase.com/docs/guides/platform/free-project-pausing): 7일간 낮은 활동 시 정지 가능. 심사 전후 실제 참가자 흐름과 DB 상태를 점검하고 덤프/복원 계획을 마련한다. 무료 플랜이 무중단을 보장한다고 주장하지 않는다.
- [Render Free](https://render.com/docs/free): 웹서비스 무요청 15분 후 절전, 무료 DB 30일 만료. 이번 예약 작업을 무료 웹 프로세스에만 맡기는 안은 추천하지 않는다.
- [Vercel Hobby](https://vercel.com/docs/plans/hobby): 개인·비상업 사용 범위다. 이번 개인 심사용 데모 후보이며 실제 사업 출시 단계에는 플랜을 재검토한다.
- [Supabase Realtime 권한](https://supabase.com/docs/guides/realtime/authorization): 실시간 접근 권한 정책이 필요하다. 참가자 아닌 사용자와 관리자 권한 구분을 검증한다.

### Q10. 어디에 배포할까?

시나리오: 심사위원이 배포 링크에 접속하고 FastAPI가 DB에 신청을 저장하며 마감 후 자동 매칭과 채팅 안내가 실행된다.

왜 지금: 내일의 최초 배포 작업, 환경변수, DB 연결, CI/CD와 비용 관리가 공급자 선택에 달려 있다.

- A. Vercel + Railway + Supabase: 화면·상시 Python 실행·DB/인증/실시간 기능을 서비스별로 맡겨 빠르게 구성한다. 공급자 세 곳의 설정·연결 관리와 Supabase 무료 정지 조건을 고려해야 한다.
- B. Vercel + Render 유료 API/작업 실행기 + Supabase: 서버 실행 비용의 예측성이 좋아질 수 있다. API와 실행기 각각의 유료 비용을 확인해야 하고 무료 웹 절전으로 대체하면 예약 동작이 불안정해진다. 요금 합계는 아직 산출하지 않았다.
- C. AWS 중심 구성: 직접 클라우드 배포 경험을 넓힐 수 있다. IAM·네트워크·DB·배포 설정 시간이 늘어나므로 이번 일정에는 부담이다. 비용이 반드시 더 싸거나 비싸다고 단정하지 않는다.

**AI 추천**: A. 업무 신뢰성 경험을 구현·검증하는 데 시간을 쓰고 운영 도구 구축을 줄인다. 월 3~5만원 상한을 목표로 무료 DB에서 시작하되 Railway 실측 사용량과 심사 기간 DB 가용성을 확인한다. 공급자별 한도와 비용을 확인한 추천이며 예산 충족 보장은 아니다.

사용자 답변: pending

결정/설계 영향: pending. 선택 후 호스팅/DB/Auth/Realtime 책임과 한계를 ADR로 기록한다.

### Q11. 예약 매칭·알림은 별도 실행기가 처리할까?

시나리오: 확정 API가 끝난 뒤 서버가 재시작되거나, 리마인드 발송 중 중단된다. 예정된 작업이 사라지지 않고 다시 처리되어야 한다.

왜 지금: 예약 작업을 API 프로세스에 두는지, 별도 실행기에 두는지가 배포 서비스 수와 장애 복구 테스트를 결정한다. 공급자와는 별개로 책임 형태를 선택할 수 있다.

- A. API + 별도 상시 실행기: 한 Python 코드베이스를 두 실행 방식으로 배포하고 DB에 예약 작업·재시도 상태를 저장한다. 재시작 복구와 API/작업 장애 분리를 검증하기 좋다. 실행 서비스와 메모리 비용이 추가된다. DB 임대 만료·작업 중복 방지 설계가 필요하며 Redis/Celery를 필수로 추가하지 않는다.
- B. API 프로세스 내부 실행: 배포 서비스 수와 기본 메모리 사용량이 작다. 재시작·스케일 변경에 맞춘 DB 기반 잠금/복구가 필요하고 CPU 매칭이 API 응답을 방해하지 않게 해야 한다. 메모리 타이머만으로 예약을 저장하는 안은 아니다.
- C. 공급자 Cron으로 주기 실행: 상시 실행기 운영을 줄일 수 있다. 공급자별 최소 간격·실행 지연·중첩/누락 동작에 맞춰 DB 작업 복구와 멱등성을 설계해야 한다.

**AI 추천**: A. 재실행·중단 복구를 핵심 성과로 삼기로 한 목표와 맞는다. 구체 작업 라이브러리, 트랜잭션·lease·재시도 및 데모 시간 제어는 후속 결정이다. 별도 실행기는 코드베이스를 나누는 별도 서비스 아키텍처 도입을 뜻하지 않는다.

사용자 답변: pending

결정/설계 영향: pending. 답변 후 배포 구조를 확정하고 초기 배포 완료 기준과 실패 재현 테스트를 좁힌다.

## Q10 후속 — 인프라 단순화

사용자 답변: “너무 복잡한데? typescript 단일로 안해서 그런가>”

해석: 인프라 구성 복잡성에 대한 설명 및 단순화 요청이다. TypeScript + FastAPI 결정 철회나 Q10/Q11 선택으로 해석하지 않는다. 공급자·실행기 형태는 여전히 pending이다.

설명: 두 언어는 빌드·개발 환경을 추가하지만 두 웹 호스팅을 필수로 요구하지 않는다. 이전 추천은 화면 호스팅·API·실행기·관리형 DB/인증/Realtime을 분리해 편의를 얻는 대신 연결 설정과 운영 표면을 늘렸다. TypeScript 단일이어도 DB·인증·실시간·예약 실행 책임은 남는다.

**AI 수정 추천**: 별도 Vercel을 제외하고 Railway에서 FastAPI가 TypeScript 화면의 빌드 파일까지 제공하며, Supabase가 PostgreSQL·Auth·Realtime을 맡는 두 플랫폼 구성을 우선 검토한다. 예를 들어 React + Vite의 정적 화면 빌드를 FastAPI에서 제공할 수 있다. 이 안을 선택하면 프론트는 별도 Node 서버/SSR을 요구하지 않는 구성으로 제한한다. React/Vite는 이번에 새로 제안한 후보이며 아직 확정하지 않았다.

- 단순화안: Railway(화면+API, 작업 실행기 형태는 Q11에서 결정) + Supabase(DB/Auth/Realtime). 하나의 앱 URL, 화면과 API의 공동 배포로 호스팅 설정을 줄인다. 프론트 변경에도 Python 앱 배포가 필요하며 화면 배포와 API 장애가 묶인다. 같은 Railway 안에 별도 실행기를 둘 경우 배포 서비스는 추가된다. 두 플랫폼이 두 프로세스라는 뜻은 아니다.
- 이전안: Vercel + Railway + Supabase. 화면 독립 배포와 호스팅 편의가 있지만 플랫폼/도메인/연결 설정이 늘어난다.
- TypeScript 단일로 재선택: Python 실행 환경이 사라져 언어 관리가 줄어든다. 기존 FastAPI 업무 서버 결정을 변경하는 선택이며 DB·인증·예약 작업까지 사라지는 것은 아니다.

시나리오: 참가자와 운영자가 같은 앱 URL에 접속하고 `/api`를 통해 FastAPI 업무 처리를 사용한다.

왜 지금: 최초 배포 전에 운영 플랫폼 수와 화면 배포 방식을 줄일지 결정해야 하며, 구현 후 뒤집으면 빌드/배포를 바꿔야 한다.

질문: 기존 TypeScript + FastAPI 방향을 유지하고, 화면과 API를 Railway에 함께 배포하는 단순화안으로 Q10을 조정할까?

사용자 답변: pending

결정/설계 영향: pending. Q11의 API/실행기 배치는 미결정으로 유지한다. 플랫폼 수 단순화만으로 재시작 복구·멱등성이 자동 해결된다고 주장하지 않는다.

사실 근거: [Vite 빌드](https://vite.dev/guide/build)는 정적 호스팅 가능한 화면 파일을 만들고, [FastAPI StaticFiles](https://fastapi.tiangolo.com/tutorial/static-files/)는 정적 파일 제공을 지원한다. 화면 경로 새로고침·API 경로 분리·푸시 서비스워커 경로는 실제 구현에서 검증해야 한다.

## Q10 후속 — 배포 플랫폼 한 곳

사용자: “배포 플랫폼은 하나만 쓸 수 없나...흠...”

해석: 플랫폼 통합 가능성 질문이다. Railway 단독 또는 인증·채팅 자체 구현을 승인한 것으로 해석하지 않는다. 기존 TypeScript 화면 + FastAPI 업무 서버 결정은 유지한다.

**AI 수정 추천**: Railway 한 프로젝트에 화면 빌드를 제공하는 FastAPI 앱, PostgreSQL을 함께 두는 구성을 추천한다. 별도 실행기를 선택하면 같은 프로젝트에 추가한다. 공급자 한 곳이 프로세스나 서비스 한 개를 뜻하지 않으며 앱과 DB는 분리한다. Vercel·Supabase·Redis는 이 후보안의 필수 구성에서 제외한다. GitHub는 코드·CI 용도로 계속 사용하며 Web Push의 브라우저별 전송 인프라까지 없앤다는 의미는 아니다.

왜 지금: 플랫폼 수와 직접 구현할 기능의 균형을 정해야 내일 DB·로그인·채팅 연결 계획을 확정할 수 있다.

- A. Railway 단독: 앱·DB·실행기를 한 대시보드에서 관리한다. 인증은 검증된 라이브러리로 테스트 계정 로그인·세션·권한부터 구현하고, 채팅은 DB 영속 저장 및 연결/권한/재연결을 검증한다. 구체 인증·실시간 라이브러리는 미정이다. 외부 관리형 인증/Realtime 대신 직접 연결·검증할 책임이 늘고 PostgreSQL 백업·복원도 관리한다.
- B. Railway + Supabase: DB·Auth·Realtime을 관리형 서비스로 활용해 해당 구현을 줄인다. 플랫폼 두 곳과 연결·무료 플랜 제약이 남는다.

**추천과 이유**: A. 사용자는 운영 플랫폼 수를 줄이려 하고 기존 서버·인증 경험이 있다. 심사용 테스트 계정과 단일 앱 규모를 활용해 로그인/채팅 범위를 좁히는 대신 데이터·권한·복구 검증은 보존한다. 한 플랫폼이 전체 구현량이나 비용을 반드시 줄인다고 주장하지 않는다. DB 비용은 무료 Supabase를 쓰는 이전안과 달리 Railway 사용량에 포함된다.

질문: Railway 단독으로 통합하고, 인증·채팅은 라이브러리를 활용해 앱 안에 구성하는 방향으로 Q10을 확정할까?

사용자 답변: “엉엉 그렇게 하자” — Railway 단독 통합안에 동의.

결정/설계 영향: Railway 한 프로젝트에 화면+FastAPI 앱과 PostgreSQL을 배포하는 안 확정. ADR-0004에 기록. Q11 실행기 배치와 인증/채팅 세부 구성은 후속 결정이다. 핵심 결정 미완료이므로 /to-spec 준비 완료라고 선언하지 않는다.

근거: [Railway PostgreSQL](https://docs.railway.com/databases/postgresql)은 Railway 프로젝트 안에 DB 서비스를 배포할 수 있으며 백업과 상태 점검을 요구한다. [백업/복원](https://docs.railway.com/guides/postgres-backups-restores)은 백업 기능 구성 및 복원 검증을 설명한다. [FastAPI 배포](https://docs.railway.com/guides/fastapi)도 지원한다. 비용은 앱·DB·실행기의 실제 사용량 합산이므로 첫 배포 때 월 3~5만원 목표와 비교한다.


## 렌더링 방식 설명 — SSR 질문

사용자 질문: “아 이러면 SSR인거지?”

설명: 현재 정적 화면 배포 제안은 CSR이다. FastAPI는 HTML/JavaScript/CSS 빌드 파일을 보내고 브라우저가 JavaScript로 화면을 그린다. SSR은 서버가 요청 시점에 화면 내용을 렌더링해 HTML을 보내는 방식이다. 서버가 파일을 제공한다는 사실만으로 SSR은 아니다.

예시: FastAPI가 화면 파일 제공 → 브라우저 화면 실행 → `/api`로 신청·매칭 데이터 요청 → 브라우저가 데이터 표시. 로그인·권한·업무 처리는 서버 책임이며 CSR이라고 브라우저를 신뢰하지 않는다.

TypeScript 화면 + FastAPI는 SSR/CSR을 자동 결정하지 않는다. React + Vite 정적 앱이 현재 추천 후보이고 프론트 프레임워크는 아직 미정이다. 이는 사용자 질문에 대한 설명이며 SSR 도입 결정이나 새로운 프레임워크 승인으로 해석하지 않는다. 참가자·어드민 중심 MVP에는 CSR을 추천하며, 별도 SSR 서버를 추가하면 렌더링/배포 구성이 늘어난다.

참고: [Vite production build](https://vite.dev/guide/build), [FastAPI StaticFiles](https://fastapi.tiangolo.com/tutorial/static-files/). Q11 예약 실행기, 인증/채팅 라이브러리 및 매칭 정책은 여전히 후속 인터뷰가 필요하다.

## 다음 설계 라운드 — 화면·실행기·규모

확정된 전제는 TypeScript 화면 + FastAPI 핵심 업무 서버, Railway 단일 플랫폼, 운영 자동화 신뢰성 중심의 검증이다. 이번 질문은 세 개다. 서로의 답을 가정하지 않고 화면 방식, 작업 책임 분리, 목표 데이터 규모를 각각 결정한다. 알고리즘/작업 라이브러리와 자원 크기는 이번 답변 이후에 선택한다.

### Q12. 화면은 React + Vite의 CSR로 만들까?

시나리오: 참가자는 모바일에서 로그인해 현재 신청 상태와 단체방을 보고, 운영자는 같은 앱의 어드민에서 예외를 확인한다.

왜 지금: Railway에서 FastAPI가 화면 빌드 파일도 제공하려면 프론트가 별도 렌더링 서버 없이 동작하는지 정해야 한다.

- A. React + Vite, CSR: 브라우저가 화면을 그리고 FastAPI 데이터를 받아 표시한다. 화면 빌드를 FastAPI 앱에 포함해 한 앱 서비스로 배포할 수 있다. 첫 화면 로딩·라우팅 새로고침·로그인 상태·모바일 UX를 직접 검증해야 한다. 검색 노출 중심 페이지에는 추가 설계가 필요할 수 있다.
- B. Next.js SSR: 요청 시 서버가 화면 HTML을 생성하는 구성을 사용한다. 초기 HTML과 공개 페이지 검색 노출을 다루기 좋지만 Python 업무 서버 외에 Node 실행 환경과 화면 서버의 인증·배포 연결이 추가된다. Next.js가 반드시 SSR만 가능한 것은 아니며 정적 내보내기도 있지만 이 선택지는 SSR 사용을 비교한다.

**AI 추천**: A. 참가자/운영자 업무 화면 중심 MVP에 맞춰 배포 실행 환경을 줄인다. 구체 UI 컴포넌트 라이브러리는 후속 구현 선택이며 지금 비교를 확대하지 않는다.

사용자 답변: “A”

결정/설계 영향: React + Vite CSR 확정. ADR-0005에 기록.

근거: [Vite 빌드](https://vite.dev/guide/build), [FastAPI StaticFiles](https://fastapi.tiangolo.com/tutorial/static-files/). SSR의 검색상 이점은 모든 페이지/검색엔진에 대한 결과 보장이 아니다.

### Q11 재제시. 자동 매칭·알림은 API와 별도 실행기로 둘까?

시나리오: 마감 시각의 매칭 중 API를 새 버전으로 배포하거나, 리마인드 발송 중 실행기가 재시작된다. 작업이 사라지거나 테이블·메시지가 중복 생성되어서는 안 된다.

왜 지금: Railway 프로젝트에 앱·DB 외에 실행 서비스 하나를 더 만들지, 장애 복구 테스트의 경계를 어떻게 둘지 결정한다.

- A. 별도 상시 실행기: 같은 Python 코드베이스를 API용·작업용으로 나눠 실행한다. 작업 장애가 API에 미치는 영향을 줄이고 재시작/중복 실행을 독립 검증하기 좋다. 서비스와 메모리 비용, 배포 연결 관리가 추가된다.
- B. API 안에서 실행: 앱+DB로 배포 구성이 가장 작다. API 배포와 작업 실행이 함께 중단되고, 중복 실행·CPU 연산의 응답 영향과 재시작 복구를 함께 다뤄야 한다.
- C. Railway Cron 주기 실행: 상시 실행기 운영을 줄인다. 공식 최소 5분 간격과 지연/직전 실행 미완료 시 생략 조건을 고려해야 하며 짧은 데모와 빠른 재시도에는 불리하다.

**AI 추천**: A. 같은 Railway 대시보드와 같은 Python 코드에 두되 실행만 분리한다. DB에 예약·진행·재시도 상태를 저장하고 중단 후 복구를 검증한다. Redis/Celery 도입을 이 결정에 묶지 않는다. 라이브러리와 작업 잠금·재시도·알림 중복 처리 방식은 후속 결정이다. 최종 외부 전달의 exactly-once를 약속하지 않는다.

사용자 답변: “A”

결정/설계 영향: 같은 코드베이스의 별도 작업 실행기 확정. ADR-0006에 기록. 구체 라이브러리와 비용은 후속 확인.

근거: 앞선 Q11과 [Railway Cron](https://docs.railway.com/cron-jobs), [요금 구조](https://docs.railway.com/pricing/plans).

### Q13. 한 번의 매칭 실행에 몇 명까지 검증할까?

시나리오: 복수 날짜·지역 선호와 제외 관계를 가진 후보 전체를 하나의 매칭 실행에서 처리한다. 운영자 누락 없이 결과와 실패 이유를 확인한다.

왜 지금: 목표 규모가 탐색 알고리즘, 제한 시간과 성능 테스트 크기를 결정한다. 제공될 수 있다는 익명 데이터의 실제 규모는 미확인이다. 아래 숫자는 실제 사용자 수를 추정하는 것이 아니라 우리가 책임지고 검증할 범위를 선택하는 것이다.

- A. 실행당 최대 50명: 작은 데이터와 장애 재현에 집중하기 좋다. 규모에 대한 증명은 제한된다.
- B. 실행당 최대 100명: 복수 테이블·미매칭·재배치 성능을 비교할 규모다. 50명보다 조합 탐색 부담이 커진다.
- C. 실행당 최대 300명: 더 큰 규모의 근거를 확보한다. 성능 개선과 케이스 설계가 개발 시간을 침범할 위험이 크다.

**AI 추천**: B. 100명은 검증 목표이며 처리 가능성을 이미 확인했다는 뜻은 아니다. 작은 데이터는 독립 완전 탐색으로 정답을 비교하고, 100명은 필수조건·중복 배치·미배치 누락·처리시간 및 성공률을 측정한다. 점수 정의/최적화 목적과 실행 시간 상한은 답변 후 별도 결정한다. 후보가 목표를 초과할 때 버리거나 잘라 매칭하지 않으며 초과 정책도 후속 설계에 포함한다.

사용자 답변: “B”

결정/설계 영향: 한 번의 매칭 실행에서 최대 100명 성능 검증 목표 확정. 작은 데이터 정답 비교와 필수조건 검증도 유지한다. 목표를 넘는 입력 처리 정책은 미정.


## 실제 신청 폼 수신 후 라운드

[화면 관찰과 사용자 설명](./application-form-reference.md)을 참고 자료로 기록했다. 사용자 수집 요청은 이름·연락처·Instagram ID·나이·성별·직업·MBTI·관심사·본인 성향이다. 추가 항목을 성향 매칭 점수에 넣는 결정으로 해석하지 않는다. 폼의 실제 선택지는 기록했지만 필수 여부·날짜 단일 선택·퇴장 문구를 PRD 정책 변경으로 자동 반영하지 않는다.

차이: 사용자 관심사 목록은 독서와 글쓰기를 분리한 11개, 화면은 합친 10개다. 사용자 목록을 우선 기록한다. PRD의 복수 날짜 선택과 알레르기 입력은 유지한다. 폼의 3회권은 PRD 구독 이용권과 의미가 다를 수 있다. 식사 후 퇴장 허용은 PRD 당일 퇴장 제한과 차이가 있다. MBTI 입력 자유 텍스트와 PRD 복수 선택 문구의 해석도 미정이다.

### Q14. 3회권과 구독 이용권의 차이를 어떻게 처리할까?

시나리오: 화면에서 3회권 15,000원·2개월 이내 사용을 구매하고 기존 3회권으로 신청한다. PRD는 1회권 또는 구독 이용권을 선택할 수 있어야 한다고 요구한다.

왜 지금: 횟수권·기간권·정기갱신은 서로 다르며 이용권 소비, 일정 이동, 실패 후 보관과 환불의 설계가 달라진다.

- A. PRD 우선: MVP는 1회권 + 모의 구독 이용권, 실제 3회권은 참고/후속 범위로 둔다. 구독 문구를 보존하지만 현행 운영 상품을 그대로 재현하지 않는다. 구독 기간·갱신·이용 한도는 후속 결정이며 실제 자동결제를 뜻하지 않는다.
- B. 현행 운영 우선: 1회권 + 2개월 유효 3회권 및 잔여권 사용으로 구성한다. 기존 폼과 일치하고 정기결제가 없어 단순하다. PRD 구독을 정기갱신으로 요구하면 부족할 수 있어 범위 차이를 명시하고 확인이 필요하다. 2개월의 정확한 만료 기준도 후속 결정이다.
- C. 모두 제공: 구독 요구와 현행 상품을 함께 다룬다. 상품별 소비·환불·만료 상태와 검증이 늘어난다.

**AI 추천**: A를 PRD 충족 기본안으로 유지하되, 3회권이 구독이라는 용어로 쓰인 것인지 확인되면 B로 좁힌다. 현행 폼의 관찰만으로 정기결제가 필수 또는 불필요라고 단정하지 않는다. 사용자는 지금 제품 범위 우선순위를 결정할 수 있으며, 확인되지 않은 외부 답을 추정하지 않는다.

사용자 답변: “PRD 우선”

결정/설계 영향: PRD 우선의 1회권 + 모의 구독 이용권으로 확정. 기존 폼의 3회권은 MVP 상품에 자동 추가하지 않는다. 구독 기간·한도·갱신 규칙은 아직 미정이다. ADR-0007에 기록.

### Q15. 본인 성향과 희망 상대 성향을 어떻게 점수로 연결할까?

시나리오: A는 ‘잔잔하고 조용한 편’이면서 ‘나와 다른 자극을 주는 사람’을 원한다. B는 ‘활기차고 에너지 있는 편’이고 C는 ‘잔잔하고 조용한 편’이다. 희망 상대 성향을 단순 공통 태그로 비교하면 의도와 다른 점수가 나올 수 있다.

왜 지금: 성향의 의미를 먼저 정해야 매칭 점수와 참가자 설명, 작은 데이터 정답 검증 기준을 만들 수 있다. 성향은 선호 조건이며 불일치를 새 Hard Constraint로 추가하지 않는다.

- A. 명시적 규칙표: 본인/희망 상대 각 선택지 사이의 대응을 정해 방향별 점수를 산정하고 테이블 단위로 합친다. 테스트와 설명이 쉽다. ‘열정’ 등 직접 대응하지 않는 표현은 보수적인 규칙이 필요하다.
- B. LLM 판단: 설명을 보내 어울림 점수를 받는다. 표현 확장이 쉽지만 재현성·비용·실패 처리와 독립 검증이 어려워진다.
- C. 모두 같은 태그로 바꿔 유사성만 계산: 구현은 작지만 ‘다른 자극’ 같은 의도를 놓칠 수 있다.

**AI 추천**: A. 깊은 대화/유머/에너지/차분함 등 직접 대응 가능한 부분부터 명시하고, 유사성과 차이를 원하는 선호를 구별한다. 점수·방향별 통합·중립값은 다음 매칭 정책 라운드에서 정한다. 사람의 심리적 궁합이 과학적으로 증명됐다고 주장하지 않는다.

사용자 답변: “A”

결정/설계 영향: 명시적 성향 대응 규칙표 사용 확정. 점수·통합 방식은 미정이며 LLM 매칭 판단은 채택하지 않는다. 성향은 선호 조건을 유지한다.


## 인터뷰 분량 조정과 Workspace 계획

사용자: “아니 오늘 너무 많이 정하면 내일 blaybus로 일정관리하는건 어떻게 하지?” 이어서 “그럼 내일 할일은 뭐야? 계획표를 한번 보여줘. 그게 결국 blaybus workspace에 들어가니까”.

응답 방향: 오늘 새 설계 질문은 더하지 않는다. 인터뷰 완료나 전체 /to-spec 준비 완료로 선언하는 것은 아니며 미정 정책은 해당 기능 Work의 선행 Task로 남긴다. 오늘의 설계 결정과 내일부터의 구현 완료는 구분한다.

[Blaybus 등록 초안](./blaybus-plan.md)을 작성했다. 다음 개발 세션은 3시간을 가정해 계획/최초 배포 명세 25분, 프로젝트·CI 60분, Railway 배포 75분, 결과/다음 작업 기록 20분으로 제안한다. 이는 사용자의 확정된 가용 시간이 아니며 실제 시간을 추정해서 기록하지 않는다. 오늘 작업을 내일 한 것처럼 기록하지 않고 준비 결과/실제 날짜를 따로 등록한다.

전체 10/20 완료 목표의 가용 시간은 아직 검증되지 않았다. 특히 10/18 일정이 바쁘므로 달력상 날짜만 배정했다고 완성 가능성이 확인된 것은 아니다. 초안은 후속 명세와 실제 투입 가능 시간에 따라 조정한다. Blaybus에 외부 게시하지 않았으며 구현 코드·인프라·Issue도 생성하지 않았다.

## 재개 — Blaybus 구조와 GitHub 연결

사용자 요청: “blaybus에 아젠다 -> 워크 -> 태스크를 어떻게 만들까? 그거 연동이 핵심인 거 같아서”, “Github 레포 생성 ㄱ?”.

읽기 전용 확인: 기존 비공개 `InryeolChoi/SerenTable` 저장소와 원격 커밋을 확인했다. 중복 생성하지 않는다. 이후 문서는 로컬에 있고 `data/`가 새로 보이나 이번 요청에서 읽거나 업로드하지 않는다. 코드 작성 및 Issue 생성 금지를 해제하는 요청으로 추정하지 않는다.

전용 Blaybus 플러그인 검색은 결과 없음. 읽기 전용 조사 에이전트가 공식 공개 자료에서 계층형 작업·시간 기록은 확인했으나 GitHub 자동 동기화/API/webhook/MCP 지원을 확인하지 못했다. 로그인 UI는 아직 미확인이다. 링크 연결을 먼저 추천하고 지원 가능성 미확인을 불가로 단정하지 않는다. 상세 초안은 [Blaybus 계획](./blaybus-plan.md)에 반영했다.

### Q16. Agenda는 기능/성과별로 고정할까, 날짜별로 나눌까?

왜 지금: 최상위 구조를 정해야 Work/Task를 등록하며 일정 변경 때 재분류를 줄일 수 있다.

- A. 성과별: 기반 / 신청·결제 / 매칭·실패 해결 / 안내·피드백 / 예외·검증·제출. Work에 목표일을 둔다. 요구사항과 결과를 찾기 쉽지만 하루 작업은 일정/필터나 작업 설명으로 묶어야 한다.
- B. 날짜별: 10/16, 10/17 등으로 Agenda를 나눈다. 당일 할 일은 찾기 쉽지만 미완료 이월과 기능 전체 진행 추적이 번거롭다.

**AI 추천**: A. 오늘 한 결정과 내일 구현을 같은 제품 목표 아래 서로 다른 Task로 기록하고 첫 세션의 Task만 상세화한다. 첫 Work의 예시와 완료 기준은 계획 문서에 제시했다.

사용자 답변: “agenda는 기능·성과별로 가자”

결정/설계 영향: 기능·성과별 Agenda 확정. 그 안에 Work, 각 Work 안에 Task를 두는 3단계 구조로 정리한다. 실제 Blaybus에는 아직 생성하지 않았다.

### Q17. GitHub Issue 없이 Task와 PR을 연결할까?

왜 지금: 업무 상태를 두 도구에 중복 입력할지 정해야 운영 부담과 추적 기준이 명확해진다.

- A. Blaybus Task ↔ GitHub PR/CI/문서 링크: 일정·시간·진행은 Blaybus, 구현·리뷰·검증 근거는 GitHub. 입력이 적지만 링크와 완료 상태는 실제 작업 후 갱신해야 한다.
- B. Work 단위 GitHub Issue도 사용: Issue 아래 PR 추적이 쉽다. Blaybus와 상태·설명 중복 관리가 생긴다. 기존 Issue 생성 금지를 바꾸는 선택이며 승인 전 생성하지 않는다.

**AI 추천**: A. 먼저 교차 링크로 시작하고 실제 연동 설정에서 공식 지원을 확인하면 자동화를 추가 검토한다. 개발/검증보다 연동 시스템 개발에 시간을 쓰지 않는다. PR과 Task의 강제 1:1 관계는 두지 않는다.

사용자 답변: “A로 가는게 맞을 거 같아” — Issue 없이 Task와 PR/CI/문서 교차 링크.

결정/설계 영향: Blaybus는 일정·실제 시간·진행, GitHub는 코드·리뷰·검증 근거를 맡는다. Issue 생성은 하지 않는다. 자동 동기화는 미확인이다.


## 계층 확인 및 data 자료 검토

사용자: “가상데이터와 로고의 기반이 될 이미지를 전부 data 폴더 안에 넣었어”, 이어서 “아젠다 안에 워크가 있고 태스크가 있는 형태인 거 같아”.

확인: Agenda > Work > Task의 포함 관계를 트리로 정리한다. 계층 변경 요청이 아니라 앞선 표의 포함 관계를 명확히 하는 설명으로 이해한다. [계획 문서](./blaybus-plan.md)에 확정 상태와 트리를 반영했다.

읽기 전용 자료 검토: 가상데이터 xlsx 한 개와 이미지 세 개를 확인했다. 이름 열이 있는 응답 행은 294개, 서로 다른 이름 문자열은 258개다. 같은 이름의 행을 같은 사용자로 병합하거나 294명을 고유 참가자로 단정하지 않는다. 연락처/Instagram/직업은 모두 비어 있고 MBTI는 대소문자·복수형·오타가 섞여 있다. 연도 없는 과거 날짜와 나이를 현재 회차/출생연도로 임의 변환하지 않는다. 100명은 실행당 검증 목표이며 원본 294행을 잘라 덮어쓰지 않는다.

이미지는 우연한 식탁 홍보 포스터 한 개, 와썹하우스 사진형 이미지 한 개, 와썹하우스 로고 PNG 한 개다. PNG는 RGBA 형식이지만 실제 배경 제거 여부를 이 형식만으로 단정하지 않는다. 제공된 식탁 포스터의 크림색 글자·따뜻한 갈색 분위기를 시각 참고로 쓸 수 있으나 새 로고를 생성하거나 이미지 편집을 승인한 것은 아니다.

세부 검토 결과는 [자료 검토](./data-assets-review.md)에 기록했다. 자료 정규화/테스트 보완과 브랜드 적용을 기존 Agenda의 Work/Task로 넣되 지금 실행하지 않는다. 원본 파일은 수정하거나 GitHub로 올리지 않았다. 다음 설계 라운드에는 원본 데이터의 사용자 식별·정규화/누락값 처리 정책을 우선 다룰 수 있다.


## 수동 Workspace 갱신과 Issue 매핑 재검토

사용자: “전체 등록 트리를 기준으로 다 기록 했어”. 등록은 사용자 완료 보고이며 AI가 UI를 확인한 결과가 아니다.

사용자 지시: “지금부터는 우리가 진행하는 일이 끝날 때마다 blaybus의 task에 기록해 달라, work를 끝내달라, agenda를 수정해 달라고 꼭 이야기 해야 돼.” 이어서 “내가 blaybus를 손으로 수정해야 하기 때문에...”.

결정: 완료 결과 보고마다 사용자가 손으로 갱신할 정확한 계층 경로·기록 문구·상태·증거를 제공한다. Work 완료는 하위 완료 기준 충족 때, Agenda 수정은 실제 범위/일정 변경 때 요청한다. 사용자 실제 시간은 임의로 채우지 않는다. 상세 안내 형식은 [운영 기록](./blaybus-plan.md)에 반영했다.

### Q18. GitHub Issue는 Work 단위로 연결할까, Task 단위로 연결할까?

시나리오: Blaybus에서 ‘첫 배포·CI·DB 연결’ Work 아래 골격·DB/CI·배포 검증 Task를 진행한다. 사용자는 Blaybus를 수동 갱신한다.

왜 지금: 이후 구현 PR의 작업 기준과 두 도구의 갱신 횟수가 달라진다. 앞서 Issue 없이 운영하기로 한 Q17을 재검토하는 질문이며 지금 즉시 Issue 생성 승인으로 해석하지 않는다.

- A. Work = Issue: 중간 산출물 하나를 Issue로 잡고 하위 Task를 체크리스트와 PR/CI 링크로 연결한다. Issue 수와 중복 상태 관리가 작다. 여러 Task가 포함되므로 진행 중인 세부 작업을 본문에 명시해야 한다.
- B. Task = Issue: 작은 행동 하나가 Issue라 작업 배정과 개별 종료가 명확하다. 준비·기록·검증까지 Issue로 늘어나 수동 Blaybus와 중복 관리 부담이 크다.
- C. 기존처럼 Issue 없이 Task ↔ PR 연결: 입력이 가장 적다. GitHub에서 Work 전체의 명세와 진행을 묶어 볼 이슈는 없다.

**AI 추천**: A. Blaybus는 일정·시간·작업 상태를 관리하고 GitHub Work Issue는 완료 기준·구현 체크리스트·PR/검증 근거를 모은다. Task와 PR의 강제 1:1 관계는 두지 않는다. 중간 PR은 Work Issue를 참조하고, 하위 Task·인수 조건이 모두 충족될 때만 Issue를 닫는다. 작은 Task PR이 Work 전체를 조기에 종료하지 않게 한다. Issue 생성 범위는 선택 후 첫 실행 Work부터 구체화할 수 있다.

사용자 답변: “그렇게 하자” — Work당 Issue 하나, PR은 Task와 유연하게 연결. Task 완료 시 관련 PR URL을 작업 기록란에 남긴다.

결정/설계 영향: 기존 Issue 없는 운영을 Work당 Issue 하나로 변경한다. Task 기록의 수동 갱신은 사용자에게 요청한다. 실제 Issue/PR 생성은 이번 턴에 실행하지 않았다.

## Q18 후속 — PR과 Task 관계

사용자 질문: “흠 그럼 issue = work이고, pr = task이어야 하나?”

설명: Work와 Issue는 완료할 산출물을 묶는 추천 대응이다. Task는 실제 행동/시간 기록 단위이고 PR은 검토·병합할 변경 단위라 강제 1:1 대응은 두지 않는 것을 추천한다. 같은 기능의 구현과 테스트 Task는 한 PR에 담을 수 있고, 자료 확인·배포 검증 Task는 새 PR 없이 결과 링크로 기록할 수 있다. 하나의 Task가 여러 PR로 커지면 Task 분할을 검토하되 수만 맞추기 위해 나누지 않는다.

**AI 추천**: Issue는 Work의 목표·완료 기준·Task 체크리스트를 담고, PR은 관련 Task를 명시한다. 검토하기 작은 구현 Task는 PR 하나를 기본 후보로 삼을 수 있지만 테스트를 PR 수를 늘리기 위해 따로 떼지 않는다. 중간 PR에는 Work Issue 참조를 넣고, Work 전체 완료 전에 자동 종료하지 않게 한다. 사용자 수동 Blaybus 갱신에는 해당 PR에 포함된 Task별 수행/검증 결과를 안내한다.

사용자 답변: pending. 이 질문 자체를 Q18 선택이나 Issue 생성 승인으로 간주하지 않는다.

다음 확인: Work당 Issue 하나, PR은 검토 가능한 변경 단위로 유연하게 연결하는 운영 원칙에 동의하는지 확인한다. 그 전에는 기존 Issue 생성 금지를 유지한다.

## Q18 승인 및 실제 Task 기록 위치 확인

사용자 답변: “그렇게 하자. 대신 하나의 task가 끝나면, 관련된 PR 링크를 저기 올리는 식으로 하자구”.

결정: Work당 Issue 하나, PR은 검토 가능한 변경 단위로 유연하게 연결한다. Task 완료 시 실제 관련 PR 링크와 수행·검증 기록을 Blaybus Task에 남기도록 사용자를 안내한다. 기존 Issue 없는 정책을 이 결정으로 대체한다. Issue 생성/기존 저장소 업로드나 구현을 이번 대화에서 실행한 것은 아니다.

화면 근거: 사용자가 제공한 2026-10-15 오후 9.33.15 스크린샷에서 Agenda `개발·배포 기반 확보`, Work `요구사항·설계·자료 정리`, Task `PRD·구글폼·킥오프 차이 기록`의 포함 관계를 확인했다. Task 상세에 파일용 ‘중간 산출물’과 별도 작업 내용 기록란(2,000자 표시)이 보인다. URL은 작업 내용 기록란에 텍스트로 안내한다. 완료 버튼이 있다는 사실만으로 Task가 실제 완료됐다고 판단하지 않는다.

상태와 다음 단계: 이번에 완료한 것은 매핑·수동 기록 원칙 확정 및 로컬 문서 반영이다. PR이 아직 없으므로 임의 링크를 제공하지 않는다. 관련 Task의 기록 문구를 제공하되 준비 Work 전체 완료는 나머지 Task의 완료 기준까지 확인한 뒤 요청한다. 상세 형식은 [Workspace 운영 기록](./blaybus-plan.md)에 반영했다.

## 구현 명세·티켓 결과물 작성

작성: [구현 명세서](./mvp-implementation-spec.md)는 PRD P0·12단계, 사용자 스토리 62개, 확정 모듈/상태, 검증 목표와 미결정 사항 21개를 분리했다. [티켓 계획](./github-ticket-plan.md)은 등록한 Work 10개를 유지하며 Task·인수 기준·직접 선행 관계를 정리했다. 새 Work를 임의로 추가하지 않았다.

확인 대기: `to-spec`의 테스트 경계 확인과 `to-tickets`의 티켓 분할·의존성 확인을 한 번에 요청했다. 테스트 경계는 실제 DB를 사용하는 제품 외부 행동을 주 경계로, 작은 매칭 정답 비교를 보조 경계로 제안했다. 사용자 응답 전에는 이 제안을 확정된 검증 설계로 표시하지 않는다. 기존 구현/테스트는 없으며 검증 도구도 아직 결정하지 않았다.

현재 단계: 검토 가능한 문서 PR 준비. 발행 전 질문에 대한 응답 후 Issue를 의존성 순서로 발행하고 `ready-for-agent`를 적용하며, 기존 Work Issue나 미완료 Task를 자동 종료하지 않는다.
