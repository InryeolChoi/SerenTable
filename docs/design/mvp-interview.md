## 1라운드 — 기술 선택의 전제와 배포 목표

질문은 아래 세 개이며 서로의 답에 의존하지 않는다. 기술 스택은 아직 결정하지 않는다. 다음 라운드는 답변에 맞춘 스택·배포 구조와 매칭 정책의 주요 모호함이다.

### Q1. 직접 검토하고 고칠 수 있는 기술은 무엇인가?

시나리오: 10/19 밤에 원격 Codex가 만든 변경이 CI에서 실패했다. 본인이 원인을 이해하고 수정 방향을 판단해야 한다.

왜 지금: 익숙한 언어와 새로 배울 수 있는 범위가 스택·테스트·매칭 구현 언어 선택에 영향을 준다. AI의 코드 생성 속도만으로 선택하지 않는다.

- A. TypeScript/React 중심으로 통일: 프론트와 서버의 언어를 맞추기 쉬우나, 해당 생태계가 낯설면 학습 부담이 있다.
- B. 익숙한 Python 또는 Java/Kotlin 등의 백엔드 + 웹 프론트: 서버 판단은 쉬울 수 있으나 두 실행 환경·API 연결·배포를 관리한다.
- C. 특정 스택 경험이 거의 없음: 관리형 서비스와 작은 앱으로 시작하기 좋지만 구현 검증을 위한 학습 시간이 필요하다.

**AI 추천**: 가장 익숙한 기술을 기준으로 선택한다. 경험 차이가 작다면 TypeScript 중심의 단일 앱을 먼저 검토한다. 사용자에게 언어/프레임워크, 배포 경험, 새 기술을 배우는 데 쓸 수 있는 시간을 함께 요청한다.

사용자 답변(최신): “typescript 단일로 갈지, typescript + python으로 갈지 고민해보자. 시간이 많지 않긴 해. 당연히 파이썬으로 가도 Fastapi로 갈 거 같고...”

결정/설계 영향: TypeScript 단일과 TypeScript + Python을 비교한다. Python 채택은 미결정이며 채택 시 FastAPI가 사용자 선호 후보다. 기존 숙련도를 추정하지 않는다. 현재 승인된 언어 구성은 없고 기존 ADR-0001은 비활성 상태로 유지한다.

### Q2. 제출 MVP를 심사용 운영 환경으로 할 것인가, 실제 유료 참가자까지 받을 것인가?

시나리오: 심사위원이 배포 링크에서 신청하고 매칭·채팅·실패 해결·다음 매칭을 직접 확인한다.

왜 지금: 외부 결제·로그인·실제 식당 예약 연동의 범위와 검증 대상을 먼저 정해야 P0 구현 시간을 확보한다. PRD가 허용한 모의 기능을 사용할지에 대한 목표 결정이며, 허용 여부 자체를 재질문하지 않는다.

- A. 심사용 배포 MVP: PRD에서 허용한 테스트 계정·모의 결제/환불을 사용하고 DB 저장·스케줄러·채팅·푸시 등 P0는 실제 작동시킨다. 완주 검증에 집중할 수 있으나 실결제 운영을 증명하지는 않는다. 식당은 사전 등록한 파트너 재고를 자동 배정하며 외부 예약 연동 여부와 구분한다.
- B. 제출 시점부터 실제 유료 참가자 운영: 실제 서비스 연동 경험이 생기지만 외부 승인·실결제 예외 검증·운영 준비가 일정 위험을 키운다.

**AI 추천**: A. 10/20까지 실제 배포한 P0와 12단계 검증을 완성하고 실결제 연동은 후속 범위로 둔다. 푸시를 앱 내 알림으로 대체하거나 채팅을 화면 목업으로 축소한다는 의미가 아니다.

사용자 답변: “심사용 배포 mvp라고 보면 되는데...음 외부 연동도 있긴 해야 하지 않을까”

결정/설계 영향: 심사용 배포 MVP 목표는 확정. 외부 연동의 종류·개수는 미정. 실결제·소셜 로그인 추가가 승인되었다고 해석하지 않는다. Q5에서 가장 작은 범위 확인을 진행한다.

### Q3. 심사 기간까지 유지할 인프라 비용의 상한은 얼마인가?

시나리오: 10/21 제출 뒤에도 심사위원이 접속할 수 있어야 한다. 무료 플랜의 절전·실행 주기·사용량 한도가 핵심 자동화에 영향을 줄 수 있다.

왜 지금: 데이터베이스·백그라운드 작업·알림 서비스의 배치 방식을 결정하기 전에 예산 제약을 정해야 한다. 아래 금액은 예산 선택지이며 실제 서비스 요금 견적이 아니다.

- A. 0원: 비용 부담이 없지만 무료 한도에 맞춰 구성해야 하며 유지 조건을 점검해야 한다.
- B. 월 3~5만원 이내: 필요한 부분만 유료 옵션을 검토할 수 있으나 그 예산으로 모든 서비스를 유료화할 수 있다고 보장하지 않는다.
- C. 월 10만원 이내: 구성 선택의 여지가 넓어지지만 해커톤 규모에 비해 비용이 커질 수 있다.

**AI 추천**: B를 비용 상한으로 두고 무료부터 시작한다. 무료 플랜의 공식 제한과 실제 요금을 확인한 뒤 꼭 필요한 지출만 결정한다. 금액은 사용자가 다른 상한을 정해도 된다.

사용자 답변: “B를 상한으로 두고 하자. 이거 떨어질 가능성도 크자나. 물론 3등을 목표로 하긴 할건데...!”

결정/설계 영향: 월 3~5만원 상한, 무료부터 시작한다. 입상 여부와 무관하게 비용을 제한한다. 서비스별 요금과 과금 구조를 확인하고 불필요한 유료화를 피한다. 공급자·유료 플랜·서비스 생성은 아직 선택되지 않았다.

## 공식 기술 문서 확인 — 선택 전 참고

읽기 전용 조사 에이전트가 공식 문서로 확인했다. 아래는 사실 참고이며 사용자 승인된 스택이 아니다.

- [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers): 한 앱에 화면과 서버 API를 둘 수 있다. 이 구조가 배포 부담을 줄인다는 것은 설계상의 추론이다.
- [Supabase 요금표](https://supabase.com/pricing): Free DB 500MB, 활성 프로젝트 2개, Realtime 동시 연결 200개, 1주 비활성 시 정지, 자동 백업 미포함, API/DB 로그 1일 보관. Pro $25/월부터. 실제 결정 시 요금 및 필요한 추가 비용 재확인.
- [Supabase Realtime](https://supabase.com/docs/guides/realtime): 실시간 기능을 제공하지만 메시지 영속 저장과 참가자별 권한은 설계해야 한다.
- [Supabase Cron](https://supabase.com/docs/guides/cron): 초 단위 예약, SQL/함수/HTTP 실행 가능. 권장 동시 작업 8개 이하, 작업당 10분 이하.
- [Vercel Cron 제한](https://vercel.com/docs/cron-jobs/usage-and-pricing): Hobby는 작업당 하루 한 번, 지정 시각의 시간 범위 안에 실행되므로 분 단위 데모 자동화의 실행기로 선택할 수 없다.
- [Supabase 이메일 인증](https://supabase.com/docs/guides/auth/passwords): 기본 이메일 발송 제한이 있어 심사 계정 제공 방식에 고려해야 한다.
- [Supabase Edge Functions 제한](https://supabase.com/docs/guides/functions/limits): 요청당 CPU 시간 2초 제한. 매칭 연산을 배치하기 전에 대상 규모별 측정 필요.

## 2라운드 — 언어 구성과 추가 외부 연동 범위

### Q4. TypeScript 단일 구성과 Python 병행 중 어떤 구성을 선택할까?

시나리오: 마감 시각에 후보를 매칭하고 확정·식당·채팅·알림으로 연결한다. 10/19 밤에 배포된 매칭 작업 실패를 원격으로 진단해야 한다.

왜 지금: 실행 환경 수와 상태 변경 책임이 CI/CD, 통합 테스트와 매칭 구현 범위를 결정한다. Python 사용 여부는 아직 미결정이다.

- A. TypeScript 단일: Next.js 후보로 화면·어드민·일반 서버·매칭을 같은 언어로 둔다. 연결과 배포 검증 부담이 작다. 매칭은 필수조건 검사와 점수 평가, 제한 시간 탐색·개선 로직을 구현해야 하며 최적해를 보장한다고 주장하지 않는다. 단일 언어가 하나의 프로세스 또는 하나의 배포만을 강제하지는 않는다.
- B. TypeScript + FastAPI 매칭 엔진: 일반 업무는 TypeScript가 담당하고 Python은 후보·제약·이력을 받아 테이블 조합을 계산한다. OR-Tools 같은 최적화 도구를 사용하기 쉽다. 두 실행 환경, API 계약, 타임아웃·재시도·배포 점검이 추가된다. FastAPI는 API 프레임워크이며 매칭 알고리즘이나 영속 작업 실행기 자체가 아니다. 저장·확정 전 최종 검증은 업무 처리 쪽이 책임진다.
- C. TypeScript 화면 + FastAPI 전체 백엔드: 서버 업무와 매칭 책임이 Python에 모인다. 전체 API와 인증·채팅 연결을 구축하고 검증해야 하므로 이번 일정에는 범위가 크다.

**AI 추천**: A를 기본안으로 제안한다. 10/20 완성 목표에서는 실행 환경과 연결 지점을 줄이는 편이 유리하다는 설계 판단이다. 다만 전문 최적화 솔버 활용을 핵심 결과물로 삼고 싶다면 B가 실제 대안이다. B의 라이브러리 사용만으로 모델 정확성이나 제한 시간 내 최적해가 보장되지는 않는다. 어떤 언어든 7명을 억지로 확정하지 않고, 8명에서는 가능한 4+4 조합을 놓치지 않는 등의 검증이 필요하다.

사실 근거: [OR-Tools CP-SAT](https://developers.google.com/optimization/cp/cp_solver)는 Python을 지원하고 최적해·실행 가능 해·불가능·결과 미확정 상태를 구분한다. [Next.js Route Handlers](https://nextjs.org/docs/app/getting-started/route-handlers)는 같은 앱에 서버 API를 둘 수 있다. 언어 선택과 최적화 목표/규모는 구별하며 후자는 별도 질문에서 결정한다.

사용자 답변: pending

결정/설계 영향: pending. 언어 구성·프레임워크·매칭 라이브러리 미정. 결정 후 중요한 책임 경계를 ADR로 기록한다.

### Q5. 외부 연동은 어디까지 추가할까?

시나리오: 심사위원이 테스트 계정으로 전체 E2E를 검증하면서 실제 서비스 연결도 확인한다.

왜 지금: 사용자의 “외부 연동도 있긴 해야 하지 않을까”가 무엇을 뜻하는지 확정해야 승인되지 않은 P1 기능으로 범위를 확대하지 않는다. DB·실시간 전송·웹 푸시도 실제 외부 서비스 통신이며, 외부 연동 개수 자체는 심사 배점 항목이 아니다.

- A. 필수 동작용 연결에 집중: 관리형 DB/인증·채팅 전송과 실제 웹 푸시를 구현하고, 테스트 계정·모의 결제/환불 사용. P0 완주에 집중하지만 소셜 로그인이나 PG 결제 연동을 보여주지는 못한다.
- B. A + 실제 Google 소셜 로그인 하나: 외부 계정 로그인 경험을 보여준다. OAuth 설정과 배포/테스트 환경 콜백 검증이 추가된다. 테스트 계정은 심사용으로 유지한다.
- C. A + PG 테스트 결제/취소 연동: 결제 응답·실패·취소 연동을 보여준다. 결제 상태 검증과 외부 테스트 API 처리에 시간이 추가된다. 테스트 연동은 실결제 운영 승인이 아니다.

**AI 추천**: A. 관리형 DB/인증·실시간 채팅과 실제 웹 푸시만으로 외부 연결 경험을 확보하고 자동화 완주에 집중한다. 사용자에게 익숙한 OAuth 설정이 있다면 B를 고려한다. B 또는 C는 추가 선택으로 남기며 승인된 것으로 해석하지 않는다. 외부 연동 개수 자체가 입상 가능성을 높인다고 주장하지 않는다.

사실 근거: [Supabase Google 로그인](https://supabase.com/docs/guides/auth/social-login/auth-google), [Next.js PWA/Web Push 가이드](https://nextjs.org/docs/app/guides/progressive-web-apps). 웹 푸시는 알림 허용이 필요하고 iOS 16.4 이상에서는 홈 화면에 설치된 웹앱에서 지원한다. PWA는 브라우저 기반 웹앱에 홈 화면 설치·알림 기능을 더하는 방식이다. 앱 내 알림은 푸시 미허용/미지원 환경에서도 제공하지만, 이것을 푸시 구현의 대체로 간주하지 않는다. 실제 지원 기기에서 푸시 발송·수신을 별도로 검증한다.

사용자 답변: pending

결정/설계 영향: pending. 추가 외부 연동 대상, 시간 상한과 실패 시 범위 결정 방식이 미정. 다음 라운드는 매칭 규모·정확성 목표 및 PRD 모호함을 우선 다룬다.

### Q6. 식당 연동과 실패 처리를 어디까지 구현할까?

시나리오: 조건에 맞는 테이블이 확정됐지만 해당 지역·시간에 배정 가능한 식당 재고가 없다.

왜 지금: 외부 식당 예약 실패 생략 허용을 내부 재고 부족 처리 삭제로 확대하면 P0 충족 여부가 달라진다. 확인 없이 범위를 바꾸지 않는다.

- A. 가상 식당 재고 자동 배정 + 재고 부족 예외 유지. 외부 예약 API는 제외한다. PRD의 자동 배정·예외 흐름을 보여주면서 외부 연결 부담을 줄인다. 실제 예약 성공은 증명하지 못한다.
- B. 식당은 항상 배정 가능하다고 가정하고 모든 실패 처리를 생략한다. 구현량은 작지만 PRD 식당 부족 예외 요구를 충족하지 못할 수 있어 별도 범위 예외 확인이 필요하다.
- C. 실제 예약 서비스까지 연동한다. 실제 예약을 보여주지만 API 접근·승인·실패 처리와 검증 범위가 늘어난다. 접근 가능한 공식 API가 있다고 가정하지 않는다.

**AI 추천**: A. 외부 예약 실패와 내부 재고 부족을 구분해 Q&A의 단순화 허용을 활용하되 P0 예외 동작은 보존한다. 예약 레코드는 가상임을 구분하고 배정은 실제 저장한다. 아직 사용자 승인된 결정은 아니다.

사용자 답변: “그렇게 하자” — 직전 추천 A에 동의.

결정/설계 영향: A 확정. 가상 식당 재고 자동 배정 및 재고 부족 예외 유지, 외부 식당 예약 API 제외. ADR-0002에 기록.

## 진로 목표 반영 라운드

사용자 Q4 답변: “고민이 되는게, 나는 백엔드를 지망하는 사람(한국은 대부분 자바 백엔드가 많고, 요새 ai 때문에 파이썬 백엔드가 늘어나고 있다만은...)이고, 이 해커톤으로 상 못 타더라도 남는 경험이 분명히 있어야 하는데 ... 음 어떻게 하지”

해석: 백엔드 진로와 입상 여부에 무관한 설명 가능한 엔지니어링 경험을 기술 선택의 중요한 기준으로 삼는다. TypeScript/Python 어느 구성도 아직 선택하지 않았다. 사용자의 채용 시장 언급은 검증된 시장 통계로 취급하지 않는다.

**AI의 수정된 추천 방향**: 완성 속도만 보았던 TypeScript 단일 추천에서, 백엔드 경험 목표를 함께 고려해 TypeScript 화면 + FastAPI 핵심 업무 서버를 우선 검토한다. 단, Python/HTTP/SQL/배포 숙련도를 확인하기 전 선택을 확정하지 않는다. Python 매칭 전용은 전문 솔버 경험에는 적합하나 신청·확정·환불 트랜잭션을 Python에서 경험하는 구성은 아니다. TypeScript로도 같은 백엔드 문제와 검증을 다룰 수 있다. 어느 프레임워크를 사용했다는 사실만으로 채용 경쟁력이나 학습 성과를 보장하지 않는다.

핵심 업무 서버 제안은 한 Python 앱 안에 신청·이용권/모의결제·매칭·확정·예외 책임을 모으는 형태다. 인증, DB 운영, 실시간 전송은 관리형 서비스를 활용하는 후보이며 직접 구현을 늘리기 위한 제안이 아니다. 실행기·스케줄러·공급자·배포 수는 아직 결정하지 않았다. TypeScript 서버와 Python 서버 양쪽에서 같은 업무 상태를 수정하는 구조는 피한다는 추천이다.

### Q7. Python과 백엔드 코드를 어디까지 직접 검토할 수 있는가?

시나리오: Codex가 만든 확정 API에서 동시에 두 요청이 들어와 참가자가 중복 배치되는 오류가 난다. 본인이 코드와 DB 동작을 이해하고 수정 결과를 검증해야 한다.

왜 지금: FastAPI 업무 서버 선택이 경험 확보인지 학습 부담 증가인지 판단하려면 기존 역량을 확인해야 한다.

- A. Python API/SQL/테스트/배포를 해본 경험이 있다. Python 서버 구성을 검토하기 유리하지만 여전히 프론트 연결과 배포 부담은 남는다.
- B. Java/Spring 등 다른 백엔드 경험이 있고 Python 문법은 익숙하다. HTTP·트랜잭션 지식은 활용 가능하나 Python ORM·테스트·배포 도구 학습이 필요하다.
- C. Python이나 서버/SQL/배포가 대부분 처음이다. 학습 기회는 크지만 제한 일정의 위험도 크다.

**AI 추천**: 가장 가까운 수준을 그대로 알려준다. A/B이면 FastAPI 핵심 서버를 더 적극적으로 검토하고, C이면 TypeScript 단일에서 핵심 백엔드 문제를 검증하는 구성을 우선 검토한다. 이는 조건부 추천이고 경험을 추정하지 않는다. 선택지보다 구체적인 기존 프로젝트 경험을 답해도 된다.

사용자 답변: “Java/Spring 등 서버 경험 + Python 문법 익숙함 + 42서울에서 트랜센더스 할 때 Django 해본 적 있음. 인증 구축 등을 해본 적도 있어”

결정/설계 영향: 기존 서버·Python·Django·인증 경험 확인. FastAPI 핵심 업무 서버를 검토할 근거가 생겼지만 Q4 기술 선택은 여전히 pending.

### Q8. 이력서에서 가장 강하게 증명하고 싶은 경험은 무엇인가?

시나리오: 수상하지 않아도 프로젝트 설명에서 자신의 설계 결정과 검증 결과를 제시한다.

왜 지금: 핵심 E2E는 모두 구현하되, 추가 실험·측정·학습 시간을 어디에 쓸지 정해야 한다. 이것은 P0 기능을 생략하는 선택이 아니다.

- A. 운영 자동화의 신뢰성: 중복 실행, 동시 신청/배치, 트랜잭션, 알림 실패 재시도와 복구를 재현하고 검증한다. 백엔드 업무 설계 경험을 설명하기 좋지만 장애 시나리오 구축과 검증에 시간이 든다.
- B. 매칭 알고리즘의 품질: 제약 위반 0, 작은 데이터 최적해와 비교, 인원 증가에 따른 성공률·점수·실행 시간을 측정한다. 최적화 경험을 설명하기 좋지만 점수 모델 및 독립 비교 기준 설계가 필요하다.
- C. 둘을 동일 깊이로 강조: 폭넓은 결과를 보여주나 7일 일정에서 모두 얕아지거나 완성 시간을 침범할 수 있다.

**AI 추천**: A를 주력, B는 필수조건 검사와 작은 데이터 비교를 기본 검증으로 포함한다. B를 선택해도 멱등성·권한·재시도 같은 P0 안전장치는 유지한다. Q7 역량 답과 무관하게 경험 목표를 선택할 수 있다.

사용자 답변: “A를 주력으로, B는 필수조건 검사와 작은 데이터의 정답 비교까지 확보. 백엔드 지원자로서 ‘어떤 오류가 가능했고, 어떻게 막았으며, 무엇으로 검증했는지’ 설명할 결과를 남기자.”

결정/설계 영향: 운영 자동화 신뢰성을 주력으로 확정. 매칭은 필수조건 검사 및 작은 데이터 정답 비교를 확보한다. 구현량이 아니라 재현 가능한 오류·방지 설계·검증 결과를 경험 증거로 남긴다.

사실 참고: [FastAPI 자동 API 문서](https://fastapi.tiangolo.com/tutorial/first-steps/)는 OpenAPI 및 대화형 문서를 제공한다. [배포 개념](https://fastapi.tiangolo.com/deployment/concepts/)은 실행·재시작·프로세스·메모리 등의 운영 책임을 설명한다. API 문서 생성이 트랜잭션 정확성이나 신뢰성 검증을 대신하지 않는다.

### Blaybus 활용 제안

- Workspace: Agenda는 신청·결제, 자동 매칭·실패 해결, 안내·채팅·피드백, 운영자 예외·독립 검증·제출 같은 결과 단위. Work는 배포해 검증 가능한 중간 산출물. Task는 구체 행동과 완료 기준으로 나눈다.
- 각 Work에 목표일, 관련 PRD ID, 완료 기준을 두고 완료 시 PR·테스트 결과·배포 URL·실제 투입 시간을 증거로 연결한다.
- Dashboard: 개발 세션 종료 때 미완료 Work와 투입 시간 편중을 확인하고 다음 세션 우선순위를 조정한다. 진척은 실제 완료한 산출물 기준으로 기록한다. 자동 동기화/API 접근 가능성은 확인하지 않았으며 약속하지 않는다.
- 저장소는 코드·설계·검증 근거, Blaybus는 계획·실제 진행·투입 시간 기록으로 연결하는 안을 추천한다. GitHub Issue 생성은 아직 금지이며 오늘은 문서/저장소 준비 범위다.
- 이 안은 초안이며 외부 Blaybus 계정에 기록을 게시한 것은 아니다.
